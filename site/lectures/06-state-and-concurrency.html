0:00 – 0:12

One tap, two places

Week 1 ended with Patch B shipped. The app now checks the count again inside a write transaction, and the last place goes to exactly one person. The debrief also listed what Patch B leaves open. Two of those items are today's work: Sam's payment hold is never given back, and nothing stops one person from holding two places at the same event. This week adds a third.

After Week 1 a teammate made the page friendlier for students on campus Wi-Fi. When a reservation gets no answer at all, the page now sends the same request once more. It also sends a header called Idempotency-Key: a new random key for each new reservation attempt, and the same key on the retry. The server receives that header but does not use it to recognise a retry.

Maya is in the library, on bad Wi-Fi. She presses Reserve once. Her phone says You're in! Reservation #229. The festival database says she holds two places.

About this bug

We set this up on purpose, so it happens on cue. The retry is a reasonable feature; the defect is a server that treats every request as new. In the lab kit, scripts/flaky_client.py plays Maya's phone. It runs a small relay on your own laptop that waits for the server's complete answer, so the server has already saved the reservation, and then drops that answer once. The server itself is not changed.

This is a real run against the kit. First the script's view, then the server's log:

Vote (2 minutes)

Which Week 1 patch would have prevented this: Patch A (disable the button while waiting), Patch B (check again inside a transaction), both, or neither? Give one reason.

Answer

Neither. Maya tapped once, so Patch A had nothing to stop. Patch B stops two requests racing for the last place; here the second request arrived 200 ms after the first had finished, and the event had plenty of room. Each request, taken alone, did exactly the right thing. The bug is in the history: the same request, twice.

Look at the phone at +316 ms. The connection closed without an answer. From where the phone sits, three different things could have happened:

  1. The request never reached the server. Nothing was saved.
  2. The server received it and failed before saving. Nothing was saved.
  3. The server saved the reservation and the answer was lost on the way back. This is what happened to Maya.

The phone cannot tell these apart. If it never retries, cases 1 and 2 lose Maya's booking. If it retries blindly, case 3 books her twice. The HTTP standard names this problem directly:

RFC 9110 (HTTP Semantics), section 9.2.2

A client SHOULD NOT automatically retry a request with a non-idempotent method unless it has some means to know that the request semantics are actually idempotent, regardless of the method, or some means to detect that the original request was never applied.

POST, the method that creates a reservation, is not idempotent: sending it twice books twice. Today we give the server a way to recognise a repeat.

Key idea

Correctness is about every history the system allows, not about one request at a time. A request that is correct on its own can still break a promise when it arrives twice, arrives late, or arrives alongside another.

0:12 – 0:27

States and forbidden moves

Before we can say what "the same request twice" should do, we need to know what a reservation can be. In Week 1 a reservation either existed or it didn't. The kit adds cancelling, so a reservation now has a state: confirmed or cancelled. A state machine lists the states and the moves between them, called transitions. Just as important, it says which moves are forbidden.

Three things in the picture turn into code.

  • Guards. The reserve arrow carries a condition: a place must be free, and Maya must not hold one already. The first half is Patch B. The second half is new, and section 4 hands it to the database.
  • A forbidden move stays forbidden. A cancelled reservation never becomes confirmed again. If Maya changes her mind she books again and gets a new reservation with a new number. The old row stays, cancelled, so the history stays honest.
  • Cancelling twice changes nothing. The second cancel finds the reservation already cancelled and leaves it alone.

The kit enforces the cancel transition in a single SQL statement:

UPDATE reservations
   SET status = 'cancelled', cancelled_at = <now>
 WHERE id = ? AND status = 'confirmed'      -- the guard

Simplified from cancel() in app/reservations.py.

The WHERE clause is the guard. Checking the state and changing it happen in one statement, so there is no gap between check and act for another request to slip into. If two cancels for the same reservation arrive together, SQLite runs the two statements one after the other: the first changes one row, the second finds no confirmed row to change. Compare Week 1's check-then-act, where the check and the insert were two separate steps 300 ms apart.

Some operations are safe to repeat by their nature. Others are not:

OperationDone twiceSame effect as once?
Read an event (GET)reads twiceyes reading changes nothing
Cancel reservation #43the second finds it already cancelledyes
Set an event's capacity to 40sets 40, then 40 againyes
Add one place to an eventadds two placesno
Reserve a place (POST)books two placesno unless the server recognises the repeat

An operation is idempotent when doing it twice has the same effect as doing it once. RFC 9110 defines it for HTTP the same way: the intended effect on the server of multiple identical requests with that method is the same as the effect for a single such request. Cancel is idempotent by design. Reserve is not. The next section makes it so.

0:27 – 0:50

Idempotency keys, precisely

The server cannot tell a retry from a new press by looking at the request body: both say {"attendee": "Maya"}. So the client gives each attempt a name. An idempotency key is a random string the client creates for one attempt and sends, unchanged, with every retry of that attempt. The server stores the answer it gave under that name. When the name comes back, the server sends the stored answer again, a replay, instead of doing the work twice.

That one sentence hides four decisions. Each has its own test in the lab.

The four rules
  1. Scope. One key per reservation attempt, per client. The server stores answers under the pair (client, key), so two phones that happen to pick the same key never see each other's answers.
  2. Same key, different request: refuse. Once the server has booked an attempt or refused it (404 or 409), it keeps a fingerprint of what the attempt asked for (event and attendee). A key that comes back asking for something else gets HTTP 422, and nothing is saved. A malformed request, such as one with an empty name, is rejected before this step, so its key stays free.
  3. Same key at the same moment: one reservation. Two sends of one attempt that overlap must still create at most one reservation. A send that finds its attempt already answered returns that answer, even when that booking is what filled the event.
  4. One transaction. The reservation and the stored answer are committed together, or not at all.

The same flow as pseudocode. You write the real version in the lab:

reserve(event, attendee, client, key):
    if (client, key) is known:                        # rules 1 and 2
        refuse with 422 if it was for a different request
        if it was a booking: return that booking      # no check, no payment
        (it was a refusal: carry on and try again)
    count the places
    if the event is full:
        if a booking for this request is stored now:  # rule 3: did this attempt
            return it                                  #   take the last place?
        refuse with 409: full
    pay
    BEGIN IMMEDIATE                                    # take the write lock
        if a booking for this request is stored now:  # rule 3
            ROLLBACK; return it
        check places again; INSERT the reservation
        store the booking under (client, key)          # rule 4
    COMMIT; return the booking
# every look-up that finds the key for a different request answers 422 (rule 2)
# every refusal also records the key's request, so rule 2 holds after a refusal too

Rule 1: what does "one attempt" mean?

The key is chosen by the client, so the client decides what counts as "the same attempt". Get that wrong and the server, doing exactly what it should, gives wrong answers.

Choose the key (pairs, 8 minutes)

The page could fill in Idempotency-Key in four ways:

  1. a new random key for every HTTP request, retries included;
  2. one random key per browser, kept forever;
  3. the attendee's name plus the event id, for example Maya-3;
  4. a new random key each time someone presses Reserve, reused on that press's retry.

For each, predict what a correct server does in three situations: S1 the answer is lost and the page retries; S2 Maya cancels her Board Game Night place, then presses Reserve for it again; S3 Maya books Board Game Night, then presses Reserve for Open Mic. Only (d) matches what a person means by "I pressed once". Option (c) also puts a person's name into a technical identifier; Stripe's documentation advises against using personal data such as email addresses as keys. And look at (b) in S2: the server replays an answer that was true when it was first given and is false now. A replay repeats the old answer; it does not report the current state. That is correct behaviour for a retry, and a good reason never to reuse a key for a new attempt.

The kit's page adds one refinement to (d). If both sends of a press get no answer at all, the page cannot know whether Maya has a place, so it keeps that attempt open: her next press for the same event finishes it with the same key, instead of starting a second attempt that could pay again.

Rule 2: why refuse, instead of replaying anyway?

With key choice (b), Maya's press for Open Mic arrives with the key already used for Board Game Night. A server that replayed on the key alone would answer "You're in!" with the Board Game Night reservation, and Maya would walk to the wrong room. Comparing a fingerprint of the request turns a silent wrong answer into a loud error that points at the client's bug. The IETF's draft standard for the Idempotency-Key header recommends exactly this answer, HTTP 422. (That draft expired in April 2026 without becoming a standard, so treat it as careful advice, not a rule.)

Rule 3: two sends at once

The page's retry does not always wait for the first request to finish. If the phone gives up waiting too early, both sends reach the server while the first is still paying. Both look the key up, both find nothing, both pay. Only the transaction can separate them. This log is a real run of the reference solution with flaky_client.py --impatient, where the phone resends after 0.1 s:

23:33:33.902  [Maya · key e15f] checked: 0 of 5 places taken
23:33:34.003  [Maya · key e15f] checked: 0 of 5 places taken
23:33:34.207  [Maya · key e15f] payment authorised (hold-10, simulated, nothing charged)
23:33:34.210  [Maya · key e15f] reservation #237 saved
23:33:34.309  [Maya · key e15f] payment authorised (hold-11, simulated, nothing charged)
23:33:34.310  [Maya · key e15f] finished meanwhile by another request: replaying reservation #237

The second send took the write lock after the first had committed, looked again, found the stored answer, and replayed it. Maya got one place, and both sends carried the number #237. There is also a safety net underneath: the answers table holds at most one stored booking per (client, key), and a second attempt to store one fails. Without the second look, the second send's attempt to store its answer would fail, and because the answer and the reservation share one transaction, its reservation would be rolled back too. We tried that: one reservation, and an error for the second send instead of the answer. The second look turns that error into the right answer.

Two more places need the same care. First, a send can find the event full because its own resend has just taken the last place; before answering "full", it must look the key up once more. Second, whenever a look-up finds an answer, the fingerprint is compared before the answer is replayed: two overlapping sends of one key could carry different requests. Fig 6.4 shows both.

Notice the two payment holds, hold-10 and hold-11, for one place. Section 6 comes back to that. Notice also that this is one design among several, with a limit worth knowing: if a place frees up while two sends of one attempt overlap, one can be told "full" while the other books. Our design still makes at most one reservation. The IETF draft suggests answering a send that arrives while the first is still running with 409 ("still in progress"), which needs a record of attempts in progress. The agent you will meet in section 5 built a version of it: its resend waits up to 10 seconds, then answers 409.

Rule 4: one transaction

One more choice is worth writing down. Our server stores a record for every answered key, booking or refusal, but replays only bookings. A refused attempt ("the event is full") booked nothing, so its retry is simply tried again and may find a place that has freed up. Its stored record keeps the key bound to its request, so rule 2 holds for refused attempts too. Stripe's API makes the other choice: it replays failed results as well. Both are defensible. What matters is that the team picks one on purpose and tests it; the lab has a test for each half of ours.

0:50 – 1:05

Let the database say no

Keys do not solve everything. Maya opens Board Game Night in two browser tabs. She presses Reserve in the first, gets her answer, then forgets and presses Reserve in the second. The first attempt has finished, so the second press starts a new attempt with a new key, and by rule 1 it is new. (Both tabs share the browser's storage, so a press in the second tab can reuse the first tab's key while that attempt is still waiting for its answer.) The idempotency key is doing its job: these really are two requests. What is broken is a rule about the data, not about requests: a person holds at most one confirmed place per event. A rule about data belongs in the database.

CREATE UNIQUE INDEX one_active_place_per_person
    ON reservations (event_id, attendee)
    WHERE status = 'confirmed';

A unique index makes the database refuse a second row with the same values in the listed columns. The WHERE clause makes it a partial index: only rows that match it are in the index at all. Cancelled rows are left out, so Maya can cancel and book again. Without the WHERE, one cancelled reservation would block her from that event forever. SQLite has supported partial indexes since version 3.8.0 (2013).

When the second tab's INSERT hits the index, SQLite raises an error inside the transaction, the transaction rolls back, and the app answers 409 You already have a place at this event. The refusal does not depend on the app remembering to check. A script, a future endpoint, or an agent fixing data by hand hits the same wall.

The kit already has two other rules in the database, written as CHECK constraints: a condition every row must satisfy.

status TEXT NOT NULL DEFAULT 'confirmed' CHECK (status IN ('confirmed', 'cancelled')),
CHECK ((status = 'cancelled') = (cancelled_at IS NOT NULL))

One rule cannot be written as a CHECK. Capacity is a count across many rows, and SQLite's documentation is plain: The expression of a CHECK constraint may not contain a subquery. In this app, "confirmed places ≤ capacity" stays in the application, enforced by Patch B's second check under the write lock. A trigger could hold it inside SQLite, because SQLite lets only one writer in at a time, but that would be a second mechanism to design and test, and the kit does not need one. Knowing which rules the database can hold, and how, is part of the design.

The key and the index do different jobs

It is tempting to think the unique index makes the key unnecessary: after all, it also stops the lost-answer duplicate. We measured each combination with flaky_client.py (3 runs × 3 trials per cell) and two tabs pressed one after the other:

BuildLost answer, retry with the same keyOld page, no keyTwo tabs, two keys
Kit: neitherduplicate 9 of 9duplicate 9 of 92 places
Key onlyok 9 of 9duplicate 9 of 92 places
Index onlyconfused 9 of 9confused 9 of 91 place second tab: 409
Both (the lab's goal)ok 9 of 9confused 9 of 91 place second tab: 409

Confused means Maya holds exactly one place, but the retry was told 409: You already have a place, so her phone never learned its reservation number, and the server authorised her payment twice. The index protects the data. The key protects the conversation: a retry of an attempt that has already finished gets the same answer and does not pay again. (Sends that overlap can still both pay; section 6.) You need both. With no key at all, nothing can make the answer right, because the server has no way to recognise the repeat.

Quick check (pairs, 3 minutes)

For each promise, pick the lowest layer that can enforce it in AfterHours: (1) a person holds at most one confirmed place per event; (2) confirmed places ≤ capacity; (3) a retry of one press gets the same answer; (4) a reservation's status is one of two words; (5) a cancelled reservation never becomes confirmed again.

Answers

(1) Database: the partial unique index. (2) App, in this kit, under the write lock: a CHECK cannot count rows. A trigger could move it into SQLite; that is a design choice to test like any other. (3) App, backed by the database's primary key on (client, key). (4) Database: a CHECK. (5) App today, through the UPDATE's guard, which only a request through the app respects. The database can hold it too, with a table of allowed transitions and a trigger; that is the optional lab extension.

1:05 – 1:15

Force the order in a test

Week 1's original tests, in tests/test_basics.py, sent one request, waited for the answer, then sent the next. Tests like that can only ever produce the safe orders. Rule 3 is about two sends that overlap, so its test has to make them overlap, and in the dangerous order: both sends look the key up before either one saves. Week 1's tests/helpers.py already does this. hold_everyone_at_payment replaces the payment step with a gate where each request waits until the others arrive, and at_the_same_time starts them together.

def test_two_requests_with_the_same_key_at_once_make_one_reservation(client, monkeypatch):
    event = event_by_title(client, BOARD_GAMES)
    gate = hold_everyone_at_payment(monkeypatch, people=2)  # both look the key up before either saves

    outcomes = at_the_same_time(
        lambda send: reservations.reserve(event["id"], "Maya", client_id="maya-phone", key="k-1"),
        ["first send", "resend"],
    )

    assert gate.all_arrived, "the two sends did not meet at the payment gate: order not forced"
    assert all(isinstance(r, dict) for r in outcomes.values()), outcomes
    assert outcomes["first send"]["id"] == outcomes["resend"]["id"]
    assert rows_for(event, "Maya") == 1

From tests/test_retries.py in the lab kit.

A forced order tests the history you thought of. A stress run tests the timings you didn't: flaky_client.py and race.py send real requests with real delays and count what happened. The two kinds of evidence answer different questions. The forced test is deterministic and fails the same way every time. The stress run can surprise you, but a green run is an observation, not a proof: 9 of 9 trials without a duplicate says nothing about the tenth ordering that no trial happened to produce. Reading R3 shows a tool that explores every ordering of a model.

We reproduced it (demo/agent-retry-fix/takeover_race_repro.py). None of our checks forced that order; passing them was evidence about the orders they forced, and no more. Each decision is defensible. Each one is yours to accept or reject before you merge.

Key idea

A test for a concurrency rule has to create the concurrency, in the order that breaks things. Then the same tests judge your fix, a teammate's, and an agent's.

1:15 – 1:25

Undo what a rollback can't

Week 1 left one more item open: Sam loses the last place after his payment was authorised. Today's log added two more cases, a resend that paid before it replayed (hold-10 and hold-11 for one place) and a second tab that paid before the index refused it. In each case a hold was placed and no new place was booked.

Patch B's ROLLBACK cannot help. A database transaction undoes the writes made inside it, in that database. The payment provider is outside: the hold was placed by a separate call, before the transaction even began. The only way back is a new action that cancels the effect of the old one, here release(hold). That new action is called compensation.

Two points carry over from the rest of today.

  • A compensation gets retried too. If the call to release the hold loses its answer, the server will try again. So the release must itself be idempotent: releasing a released hold changes nothing. The kit's simulated payments.release() works that way.
  • Every outside call is its own retry problem. Our payment call is not idempotent either: a retried authorisation would place a second hold. Payment APIs such as Stripe's let you pass an idempotency key for this reason; Stripe's documentation says all its POST requests accept one.

Releasing holds is an optional extension in the lab. Reading R1 goes further: why "exactly once" is a promise about effects, and never about messages.

Beyond one server

The lecture stayed with one app and one database. These four readings follow the same ideas further: into networks that lose messages, clocks that disagree, a company that checks every history of its designs, and an accident where software became the last line of defence. Read them before the lab.

R1

Exactly once is a promise about effects

A sender that gets no answer has two choices. It can give up, and then the work happened at most once: maybe zero times. Or it can resend until an answer arrives, and then the work happened at least once: maybe twice. (Resending only gets there if the network and the server eventually let a request through.) Nothing the sender can choose guarantees that the work happens exactly once, for the reason Maya's phone met at +316 ms: the sender cannot tell a lost request from a lost answer.

What real systems promise instead is an exactly-once effect: keep resending until the work is confirmed, and make the processing idempotent so a repeat changes nothing. The promise has two halves of different strength. "Never twice" holds in every history. "At least once" holds only if the network comes back before the client gives up and before the server forgets the key. Your reservation endpoint after the lab guarantees the first half; the page's single retry gives the second half one extra chance. Three details decide how well the promise holds in practice.

  • How long keys live. A server cannot keep every key forever. Stripe's API documentation says keys can be removed once they are at least 24 hours old, and a key reused after that is treated as a new request. A retry that arrives after its key was forgotten is a new booking. So the key's lifetime must be longer than any client will keep retrying. The kit keeps keys forever, which the agent in section 5 also pointed out.
  • What is replayed. Our reference stores a record for bookings and for refusals, but replays only bookings; a refused request is tried again. Stripe stores results whether they succeed or fail, even server errors, and replays them all. Either choice is defensible if it is written down and tested.
  • Every hop is its own problem. An idempotent reservation endpoint does not make the payment call behind it idempotent, or the confirmation email after it. Each call that leaves your process needs its own key, or its own way to recognise a repeat. The same holds for compensations, like releasing a hold: they are retried too.
R2

Clocks and the order of events

Lecture 1's log showed Maya's and Sam's checks in the same millisecond, and its caption warned that sharing a millisecond does not make two events simultaneous. Those timestamps came from one clock on one laptop. As soon as a system runs on several machines, each with its own clock, timestamps become worse evidence of order: clocks drift, and a message can appear to arrive before it was sent.

In 1978 Leslie Lamport published "Time, Clocks, and the Ordering of Events in a Distributed System" in Communications of the ACM. Its introduction uses a familiar example: in an airline reservation system we specify that a request for a reservation should be granted if it is made before the flight is filled. However, we will see that this concept must be carefully reexamined when considering events in a distributed system. His answer was to define order without clocks. Event a happened before event b if they are in the same process and a came first, or if a sends a message and b receives it, or if a chain of such steps leads from a to b. When neither happened before the other, the two events are concurrent: it is sometimes impossible to say that one of two events occurred first.

The paper then gives a simple rule for logical clocks. Each process keeps a counter and increases it between events. Every message carries its sender's counter, and the receiver sets its own counter above that number. The result is Lamport's clock condition: if a happened before b, then a's number is smaller than b's. (The reverse does not hold: a smaller number does not prove anything happened first.)

AfterHours never asks a clock who got the last place. SQLite's single write lock puts every commit into one order, and each request decides inside that order. Lamport's own note on the paper, on his website, makes the link to today's first half: he wrote it to show how a set of computers can act like one state machine by agreeing on a single order of requests, and he remarks that few readers noticed the paper said anything about state machines.

R3

Checking every history: formal methods at Amazon

Lecture 1's strip exercise counted the orders in which Maya's and Sam's three steps can interleave: 20, of which 18 oversell. Sequential tests produce only the 2 safe orders. Today's forced test picks one bad order on purpose. A stress run samples whatever orders the timing happens to produce. None of them looks at all 20.

A model checker does look at all of them, for a small model of the design. In April 2015 Chris Newcombe and five co-authors described their experience at Amazon Web Services in Communications of the ACM, in "How Amazon Web Services Uses Formal Methods". Since 2011, they wrote, engineers at AWS have used formal specification and model checking to help solve difficult design problems in critical systems. They wrote specifications in a language called TLA+ and checked them with the TLC model checker, which explores every possible execution of a specification. At the time of writing they had used it on 10 large systems, seven teams were using it, and engineers from entry level to principal had learned it from scratch and got useful results in two to three weeks.

The most striking example concerns DynamoDB. The model checker found a bug that could lose data if a particular sequence of failures and recovery steps was interleaved with other processing. The shortest trace that showed it had 35 high-level steps, and the bug had passed unnoticed through extensive design reviews, code reviews and testing. The authors explain why such bugs survive: human intuition is poor at estimating the true probability of supposedly “extremely rare” combinations of events in systems operating at a scale of millions of requests per second.

They also give the vocabulary for the promises we wrote today. A safety property says what the system is allowed to do: one press never makes two reservations. A liveness property says what it must eventually do: every retry eventually gets an answer. Keep the scope in mind. A model checker checks a model of the design, usually with a small number of servers and requests, not your Python code; the authors say it themselves: formal methods deal with models of systems, not the systems themselves. A bug in the step from design to code is still possible. And this is Amazon's own 2015 account of its practice, not an independent study.

R4

Therac-25: when software became the last safety net

Case: Therac-25, 1985–1987

The Therac-25 was a computer-controlled radiation therapy machine. Between June 1985 and January 1987 it was involved in six known massive overdoses, at least three of them fatal. The standard account is Nancy Leveson and Clark Turner's investigation, published in IEEE Computer in 1993.

This reading is here for context, and because people were badly hurt, it deserves care. Several of the software defects Leveson and Turner describe are close relatives of this week's topic. In the software behind the accidents at Tyler, Texas, an operator who edited the treatment data quickly, within about 8 seconds while the machine was setting its magnets, could leave the machine set up differently from what the screen showed, and the software never noticed the edit. The same code had a related race: a flag recorded that data entry had finished, but, in Leveson and Turner's words, it only indicates that the cursor has been down to the command line, not that it is still there. That is a check acted on after it stopped being true. Behind the January 1987 accident at Yakima, Washington, a one-byte counter rolled over to zero on every 256th pass, and on that pass a safety check was skipped.

A third detail mirrors this week's lost answer from the other side. At Hamilton, Ontario, in July 1985, the machine stopped with an error and its display read "no dose". Believing nothing had been delivered, the operator pressed P, the proceed key, to try again: standard practice, because operators had become used to frequent malfunctions that did no harm. It happened five times in all. The patient had been overdosed.

Leveson and Turner insist that the software defects are not the whole story, and that To attribute a single cause to an accident is usually a serious mistake. The contributing factors they list include management inadequacies and lack of procedures for following through on all reported incidents, overconfidence in the software and removal of hardware interlocks (making the software into a single point of failure that could lead to an accident), presumably less-than-acceptable software-engineering practices, and unrealistic risk assessments along with overconfidence in the results of these assessments.

Hold the comparison lightly: a festival booking is not a radiation dose. But two habits from this week are small versions of their lessons. Keep more than one layer of protection, and put the strongest one where every path must pass (Fig 6.6). And treat a display, a log line or a missing answer as evidence about the system's state, never as the state itself.

W

Words from today

Idempotent
Doing it twice has the same effect as doing it once. Cancelling is; creating a reservation is not, unless the server recognises the repeat.
Idempotency key
A random string the client creates for one attempt and sends, unchanged, with every retry of that attempt.
Key scope
What one key stands for and whose it is. Here: one reservation attempt by one client, stored under (client, key).
Fingerprint
A short hash of what a request asks for, used to spot a key reused for a different request (answered with HTTP 422).
Replay
Sending the stored answer again instead of doing the work again. It repeats the old answer; it does not report the current state.
State machine
The states something can be in, the allowed moves (transitions) between them, and by omission the forbidden ones.
Guard
A condition a transition requires. In the kit, the WHERE status = 'confirmed' of the cancel UPDATE.
Partial unique index
A unique index over only the rows that match a WHERE clause, such as confirmed reservations, so cancelled rows don't count.
CHECK constraint
A condition every row must satisfy. In SQLite it may not contain a subquery, so it cannot count rows.
Compensation
A new action that undoes the effect of an earlier one that a ROLLBACK cannot reach, such as releasing a payment hold.
At most once / at least once
Send once and never resend (the work may not happen) / resend until answered (the work may happen twice).
Happened before
Lamport's order of events: earlier in the same process, or a message's sending before its receipt, or a chain of these. Events with neither order are concurrent.
Safety / liveness
What a system is allowed to do / what it must eventually do.
