0:00 – 0:15

Fast with 10 events, slow at festival scale

It is the first night of the autumn festival. At 8 pm, bookings open for the headline events. An event's own page in AfterHours (/?event=3601) asks the server how many places are left? every ten seconds while it is open, with the request GET /api/events/{id}. If about 2,000 students have an event page open, that is roughly 200 availability checks per second. (The 2,000 is a planning estimate, a number to design for; nobody measured it.)

Every demo so far ran on a handful of events and felt instant. The festival database is different. AfterHours has now run ten festivals, and nobody ever deletes a reservation, so the database holds 4,000 events and 1,000,000 reservations. The data is synthetic, made by a script so that everyone measures the same thing. The code that answers the check is Lecture 1's, with Patch B.

We sent the same request, GET /api/events/{id}, to both databases with the lab's load generator, three runs of ten seconds each.

Vote (2 minutes)

The code did not change. Where would you look first? Pick one and write down the result that would prove your guess wrong.

  1. Too many queries per request (the N+1 pattern from Week 7).
  2. Python and FastAPI are too slow for this.
  3. The laptop is too small; buy a bigger server.
  4. The database does too much work for each request.
  5. Something else.

Keep your guess. By 0:50 you will have the evidence for or against it, and none of that evidence will come from a stopwatch.

Key idea

Measure before you optimise. Find the bottleneck with evidence, fix that one thing, and measure again the same way. A fix without a before-and-after measurement is a guess with a commit message.

0:15 – 0:35

Measuring latency

Latency is the time from the moment someone asks to the moment the answer arrives. For one request it is one number. For a festival it is thousands of numbers, and they are not all the same. Here are 20 of them, picked at random from one of our runs (before any fix, 80 requests per second):

 55.7   52.1   59.0   36.7   37.9
 51.0   49.3   36.5   39.9   46.9
 36.8   36.2   41.5   41.4   36.4
 36.5   36.6   39.8   43.5   47.4   (milliseconds)
In pairs (5 minutes, calculator allowed)
  1. Work out the mean (add them up, divide by 20) and the median (sort them; the middle).
  2. Sort them and find the value that 19 of the 20 are at or below. That is the 95th percentile, or p95.
  3. Your team lead wants one number for the status report on the 8 pm rush. Which do you give, and what do you say next to it?
Answers

Mean 43.1 ms, median 40.6 ms (the average of the 10th and 11th values, 39.9 and 41.4), p95 55.7 ms. The median says what a typical person waited. The p95 says what the unlucky one in twenty waited, and at 200 checks per second that is ten people every second. The mean belongs to nobody: it mixes the fast majority with the slow few.

For the report, give the p95 with its conditions: "p95 55.7 ms at 80 requests per second, sample of 20". A sample of 20 is far too small to trust a p95, which rests on a single value. That is why the lab's runs have hundreds or thousands of requests each.

A percentile answers the question "how long did the slowest few wait?". The p50 (median) is the middle. The p95 is the time that 95% of requests beat; one in 20 was slower. The p99 leaves out only the slowest one in a hundred. The slow end of the distribution is called the tail. The picture shows why one number is never enough.

How the load generator works

The lab's scripts/load.py uses only Python's standard library. It sends requests at a steady rate, the way 2,000 phones do: each phone asks when it is due, whether or not anyone else has had an answer. (A generator that waits for each answer before sending the next would slow down whenever the server does, and would hide the very queue you are looking for.) It measures each latency from the moment the request was due, so time spent waiting behind other requests counts, as it would for a person. Every run reports four things:

It reportsWhy you need it
Achieved rate: successful answers per second, counted until the last answer came backIf it is below the rate you asked for, the server did not keep up, and the percentiles describe a different load from the one you meant
Errors: anything but a 200 OK within 5 seconds of being due: late answers, requests never sent because they were already 5 seconds overdue, other statusesErrors are left out of the percentiles, so a run with errors looks better than it was
Samples: how many requests the run countedA p99 from 50 requests is just the slowest one. You need hundreds for a p99 that means anything
p50, p95, p99, per run, for three runsThe spread between runs tells you how much a single run can mislead you

The knee

Now raise the rate step by step and watch what happens. This is a sweep: nine scheduled rates, three runs each, before any fix. The rate on the horizontal axis is the demand: how many requests load.py schedules per second.

Up to 40 requests per second the p95 stays between 34 and 42 ms: almost every request is answered as soon as it arrives. By 100 per second it has crept up to about 67 ms, as requests start to overlap. Between 100 and 120 requests per second the line bends sharply: that bend is the knee. Past it, the server cannot finish requests as fast as they arrive, so a queue forms and grows every second the rush lasts. Waits jump from tens of milliseconds to seconds, and people give up. The server keeps working at about the same pace, finishing 81 to 87 requests a second. But more and more of its answers arrive after the person has stopped waiting. We ran 200 requests per second three more times, 2,000 requests per run. In each run, load.py sent 1,249 to 1,255 of them, and 686 to 697 of those were answered more than 5 seconds after they were due. The other 745 to 751 were never sent, because they were already 5 seconds overdue when a connection came free. Only about 37 answers per second came back in time, fewer than at 100. (The split between late and never sent comes from load.py having only 50 connections; 2,000 phones would all have sent their request, and waited.)

Agent-off drill (3 minutes, no laptop)

A server can finish 100 availability checks per second. For 10 seconds, 200 arrive every second, and nobody gives up. (1) How many requests are waiting when the 10 seconds end? (2) How long does the very last one wait before the server even starts on it? (3) What happens to both numbers if the rush lasts 20 seconds?

Answer

(1) 2,000 arrive and 1,000 are finished, so 1,000 are waiting. (2) The server works through them at 100 per second, so the last one waits about 10 seconds. (3) Both double: 2,000 waiting, about 20 seconds. Past the knee, the wait grows with every second the rush lasts. That is why the lab reports the run length with every result, and why reading R2 (Little's law) is worth ten minutes.

0:35 – 0:50

Find, fix, remeasure

Back to your guesses from the vote. A stopwatch told us that the check is slow. To find out why, start with evidence that gives the same answer on every laptop with the same data and SQLite version, however busy. The lab's scripts/explain.py runs one request inside Python, records every SQL statement the request runs, and asks SQLite how it plans to answer each one (EXPLAIN QUERY PLAN). It also counts the work SQLite does, in steps: SQLite runs every statement as a small program, and a step is one of its instructions. This is real output from the festival database:

$ python scripts/explain.py

Real output; the long SQL line is wrapped to fit.

Three lines settle most of the vote:

  • One SQL statement. This request has no N+1 pattern. (And in SQLite, many small queries are not automatically a problem anyway: SQLite runs inside the app's process, so a query is a function call inside the app, with no trip across a network. Its own documentation says so. Count before you blame.)
  • SCAN r. To count the escape room's 39 reservations, SQLite reads every row of reservations, all 1,000,000, one after another. A SEARCH would jump straight to the matching rows.
  • 4,000,352 steps, about four per row in the table. On the 10-event demo database the same request, with the same plan, took 3,576 steps. The problem has been in the schema since Week 1. It only became visible when the table grew.
Predict (pairs, 2 minutes)

Event 3604 (the Maker Workshop) has 12 reservations; event 3607 (a club night) has 381. Before any fix, which one takes more steps to check? After adding an index on reservations(event_id), which one?

Answer, with the measured counts

Before the fix both read the whole table, so they take almost the same work: 4,000,136 and 4,003,088 steps. The size of the event hardly matters, because every row gets looked at. After the fix the work follows the event: 161 steps for the workshop, 3,851 for the club night. This is the lab's discriminating experiment: if the event's size mattered before the fix, the hypothesis "the database reads too much" would be in trouble.

The fix is one line

The evidence picks the fix. If the count had shown one query per event (the N+1 pattern), the usual fix would be a join: one query that fetches everything at once, which matters most when every query is a trip to a database server. Here the count shows one statement that reads too much, so the fix is an index: a sorted copy of one or more columns, with a pointer back to each row, like the index at the back of a book. With an index on event_id, SQLite can jump to one event's reservations without reading the rest.

Index reservations by eventapp/schema.sql
  CREATE TABLE IF NOT EXISTS reservations ( … );+ -- Every availability check counts one event's reservations.+ CREATE INDEX IF NOT EXISTS reservations_event_id ON reservations(event_id);
Shortened. The app runs schema.sql at every start, so the next start builds the index on the existing million rows.

SEARCH r USING COVERING INDEX: SQLite jumps to the escape room's entries in the index and counts them there, without touching the table (a covering index holds everything the query needs). The work fell from 4,000,352 steps to 431.

A check that is the same everywhere

Should the test suite check that the page is fast? A test like assert latency < 50 ms would pass on a quiet laptop and fail on a busy one, or in CI on a shared machine. It would be flaky by design. Test the thing that causes the speed instead: the plan. SQLite chooses a plan from the query, the schema and, only if someone has run ANALYZE, statistics about the data. AfterHours never runs ANALYZE, so on the same SQLite version the five-event test database gets the same plan as the festival, and this test would have caught the problem in Week 1. A new SQLite version, or collected statistics, can change a plan; that is one more reason to keep measuring.

def test_the_availability_check_uses_an_index(client):
    event = event_by_title(client, ESCAPE_ROOM)
    detail = plan(EVENT_SQL + " WHERE e.id = ? GROUP BY e.id", (event["id"],))
    assert not SCANS_RESERVATIONS.search(detail), detail   # "SCAN r" or "SCAN TABLE reservations AS r"
    assert "INDEX" in detail, detail

It fails on the kit and passes with the index. Timing stays evidence, never a gate.

0:50 – 1:10

The economics of agentic work

Point the same habits at the team. A change costs more than the minutes it takes to produce: someone checks it, fixes what the check finds, redoes what was wrong, and pays for the agent's tokens. Where does that effort go when agents write much of the code? Two sources from outside this course, read with the same care as a latency report:

METR also labelled screen recordings of 74 of the tasks. With AI allowed, developers spent a smaller share of their time writing code and reading or searching, and more time prompting, waiting for the AI (about 4%) and reviewing and cleaning up its output (about 9%). They accepted fewer than 44% of the generations offered. The typing got cheaper; checking arrived to take some of its place.

Tokens are part of the bill too, and easy to count. An agent session that reads 400,000 tokens of code and conversation and writes 20,000 tokens costs, at an illustrative $3 per million input tokens and $15 per million output tokens, $1.20 + $0.30 = $1.50. Twenty minutes of a person checking the result, at an illustrative $30 an hour, costs $10. (Prices change often and differ between providers and models; look up the current ones before you use real numbers.) On numbers like these the checking minutes cost more than the tokens, and they are the part a team can measure itself.

Key idea

Making one step faster speeds up the whole only as much as that step's share of the whole allows. If producing is 40% of a change's effort and an agent makes producing ten times faster, the change gets at most 1 / (0.6 + 0.04) ≈ 1.6 times faster. This is the arithmetic now called Amdahl's law (reading R1). It is why this course spends its time on checking.

An honest experiment

Suppose your team asks: does handing diagnosis to an agent make our fixes faster? The easy experiment is to use the agent for a month and compare with the month before. It will produce a number. The number will mix the agent's effect with everything else that changed that month.

In pairs (8 minutes): design it

Design a fair experiment for your team's question: "For a future set of comparable diagnostic tickets, does diagnosing with an agent get us to an accepted fix faster than diagnosing without one?" The tickets are hypothetical: imagine the next batch of similar bug reports your team will get. Write down: the measure (and exactly when the clock starts and stops), how tasks get assigned, how many you need, two confounders and what you do about each, and one result that would make you stop using the agent for this.

Debrief: one good design, and what to watch for

Measure: minutes from picking up the ticket to the fix being accepted by a reviewer, logged in four columns (implement, review, debug, rework), plus defects reopened within two weeks. The clock stops when a reviewer accepts the fix; the first green test is only a step on the way. Assignment: list the tickets first, then flip a coin for each: agent or no agent. Size: as many tickets as you can; with six you will learn little, and say so. Confounders: learning (the second similar ticket is easier either way; the coin spreads it over both groups), difficulty (estimate each ticket's size before the coin, and check the two groups got similar sizes), self-report (log minutes as you go, not afterwards). Stop rule: decide in advance, for example "if agent tickets take longer in total, or reopen more often, we stop delegating diagnosis".

A result against your hopes is still a result. The course marks the reasoning and the evidence, and a failed experiment with sound method can earn strong marks.

Key idea

Performance and productivity are both measured the same way: decide the question first, compare like with like, let something other than you choose the conditions, repeat, report the spread, and write down what you did not measure.

ADMIT ONE · WEEK 12

After class · about 25 minutes

Four laws and a warning

The lecture used one slow query and one table of studies. These four short readings give you the ideas underneath: two small laws that let you reason about speed with arithmetic, the most misquoted sentence in programming, and what happens to the tail when one request needs many servers. Read them before the lab.

R1

Amdahl: the part you did not speed up

In 1967 Gene Amdahl, a computer designer at IBM, argued against the idea that connecting many processors would make computers dramatically faster. Part of the work he measured was data-management "housekeeping", which he put at 40% of the instructions executed in production runs and which, he wrote, "appears to be sequential": it cannot be shared out among processors. His conclusion: the effort expended on achieving high parallel processing rates is wasted unless it is accompanied by achievements in sequential processing rates of very nearly the same magnitude.

His paper has no equations. The formula now called Amdahl's law came later: if a fraction p of the work is made s times faster, the whole becomes 1 / ((1 − p) + p/s) times faster. However large s gets, the whole can never beat 1 / (1 − p).

Amdahl wrote about processors. Applying the same arithmetic to a team's effort is our analogy, and it works because effort adds up the same way time does. If the agent speeds up only producing, then producing's share of your effort sets the ceiling. Two lessons follow. First, measure the shares before you celebrate a speed-up in one of them. Second, after a big improvement, the step you did not improve becomes the bottleneck. Today's query is an example: once the index made the SQL cheap, the rest of the request, Python and HTTP, became most of the time (R3's figure: 64%). Now even an infinitely fast SQL statement could make the request at most about 1.6 times faster, because the rest stays.

R2

Little's law: queues you can count

John Little proved in 1961 a result so simple it seems like it must be missing something. In his own later summary: the average number of items in a queuing system, denoted L, equals the average arrival rate of items to the system, λ, multiplied by the average waiting time of an item in the system, W. Thus, L = λW. It holds whatever order the queue is served in, and, as Little put it, If you know two of {L, λ, W}, you can quickly calculate the third.

Use it both ways. From our measurements: below the knee, at 60 answers per second with a mean of 37 ms, about 2.2 requests were in the system on average, waiting or being served; the p95 at that rate, 43 ms, was close to the time one check takes on its own, so few waited long. Past the knee, at 87 answers per second with a mean of 2.3 s, about 201 were inside at once: a crowd. And for planning: if 200 checks arrive each second and you want them answered in 50 ms on average, about 200 × 0.05 = 10 requests will be in the system on average, queued or in service. Whether that is achievable is a separate question about the server: how long one check takes, and how many it can work on at once. Before the fix, each check alone took over 30 ms of work; the sweep shows this laptop managed fewer than 100 a second.

Two cautions. Little's law is about averages over a long enough stretch; it says nothing about the p99. And it assumes what goes in comes out: requests that give up and leave count as leaving, which is one way a queue can look healthier than the people in it feel.

R3

The whole Knuth quote

"Premature optimization is the root of all evil" is quoted to end arguments. Here is the whole passage, from Donald Knuth's 1974 paper "Structured Programming with go to Statements":

There is no doubt that the grail of efficiency leads to abuse. Programmers waste enormous amounts of time thinking about, or worrying about, the speed of noncritical parts of their programs, and these attempts at efficiency actually have a strong negative impact when debugging and maintenance are considered. We should forget about small efficiencies, say about 97% of the time: premature optimization is the root of all evil.

Yet we should not pass up our opportunities in that critical 3%. A good programmer will not be lulled into complacency by such reasoning, he will be wise to look carefully at the critical code; but only after that code has been identified. It is often a mistake to make a priori judgments about what parts of a program are really critical, since the universal experience of programmers who have been using measurement tools has been that their intuitive guesses fail.

The short version drops "say about 97% of the time" and everything after "evil". The whole passage says: don't polish the noncritical 97%, do work hard on the critical 3%, and find out which is which by measuring, because intuition fails. (Knuth later called the phrase "Hoare's dictum", crediting Tony Hoare.) Here is our critical 3%, measured.

Before the fix, one SQL statement was 97% of the request; making anything else faster was pointless. After the fix the statement, most of it now the cost of opening a connection, is 36% of a much shorter request, and the rest, Python, FastAPI and HTTP, is the largest part. Is that worth optimising now? Only if someone is waiting on it. At 1.0 ms per request nobody is, so the right move is to stop, and to write down the budget that would make you start again.

R4

The tail at scale

A p99 sounds like a rare event: one request in a hundred. Jeffrey Dean and Luiz André Barroso of Google explained in 2013 why it stops being rare in large systems. Their example: consider a system where each server typically responds in 10ms but with a 99th-percentile latency of one second. If a request needs just one server, one in a hundred is slow. If a user request must collect responses from 100 such servers in parallel, then 63% of user requests will take more than one second.

The arithmetic: the request is fast only if every server is fast, and 0.99 multiplied by itself 100 times is about 0.37. The same happens on a single web page that makes ten requests to load: if each has a p99 of one second, and they are slow independently of each other, about one page load in ten waits for at least one slow request. Dean and Barroso's remedies include hedged requests: send the request to one server and, if no answer has come after a short delay, send the same request to a second and use whichever answers first, then cancel the other. The delay matters. One approach they describe waits until the first request has been outstanding longer than the 95th-percentile latency, which limits the extra load to about 5%.

Two lessons for AfterHours. Report the tail as well as the median, because the tail is what large systems and busy pages magnify. And count how many requests one page load makes; each one is another draw from the tail.

W

Words from today

Latency
Time from asking to getting the answer. The lab counts it from the moment a request was due.
Achieved rate
Successful answers per second that actually came back. Compare it with the rate you tried to send.
Percentile (p50, p95, p99)
The time that 50%, 95% or 99% of requests beat. p50 is the median.
Tail latency
The slow end of the distribution: the p95, p99 and beyond.
Knee
The load at which latency stops being flat and rises sharply, because requests arrive faster than they are finished.
Open-loop load
Requests sent on a schedule, whether or not earlier ones have been answered, the way many independent users behave.
Query plan
How SQLite will answer a query, shown by EXPLAIN QUERY PLAN. SCAN reads every row; SEARCH visits only some. It can change with the SQLite version and with statistics collected by ANALYZE.
Index
A sorted copy of some columns with pointers back to the rows. A covering index holds everything the query needs.
SQLite steps
Instructions SQLite executed for a statement: a measure of work that is the same on every machine for the same data and SQLite version.
Confounder
Anything other than the change you are testing that moves the result, such as learning, task difficulty or a busy machine.
Amdahl's law
Speeding up a fraction p of the work s times speeds up the whole at most 1 / ((1 − p) + p/s) times.
Little's law
L = λW: average number inside = arrival rate × average time inside.
