Inside the Agent: Delegate Like an Engineer

A coding agent is a model in a loop with tools, context and permissions. Today we open one up, write the loop ourselves, and learn to hand work to it the way an engineer does: with a task contract, and with rails that hold whatever the model decides.

Turn to your neighbour (2 minutes)

Put your finger on the uvicorn step. At that moment, what exactly did the model have in front of it? What could it not see?

Four things are worth noticing.

  1. The model never touched a file. It produced text that asked for a command. Codex ran the command and pasted the output back. The model knows your code only as the text that came back.
  2. A failed tool is just more text. rg was not installed. The error went back, and the next request used nl instead.
  3. The sandbox decided, not the model. The model asked to open a port; the harness refused. The contract's "do not modify any file" was a request. The port block was enforced.
  4. The log does not show everything. Codex's own instructions to the model and its tool definitions were in the context on every call, and they are not in the log. The usage line also counts 196 reasoning tokens over the whole run; their text is not shown.
Key idea

An agent is a model in a loop with tools, context and permissions. Anthropic's engineers describe agents as typically just LLMs using tools based on environmental feedback in a loop. Simon Willison's short version: An LLM agent runs tools in a loop to achieve a goal. Every part of it is ordinary: text, a loop, a few functions, and rules about which functions may run.

0:10 – 0:25

The loop in 40 lines

A model call is a request and a response. The request has three parts: the system prompt (standing instructions), the tools (for each one a name, a description, and a JSON Schema for its input), and the messages (the conversation so far). The response is a list of content blocks, some text and some tool requests, plus a stop_reason that says why the model stopped writing.

A tool request is only data. The model writes it; your program decides what to do with it. Here is one from the lab's first recording (the course team wrote the recordings in the API's exact format), and the result the harness sends back:

// the model's reply (stop_reason: "tool_use")
{"type": "tool_use", "id": "toolu_a_02", "name": "read_file",
 "input": {"path": "app/main.py"}}

// the harness's next message to the model
{"role": "user", "content": [
  {"type": "tool_result", "tool_use_id": "toolu_a_02",
   "content": "\"\"\"AfterHours — the campus festival platform …", "is_error": false}]}

The model keeps no memory between calls. Anthropic's documentation says it plainly: The Messages API is stateless, which means that you always send the full conversational history to the API. So the program around the model, the harness, keeps the conversation and sends all of it every time. That is the whole loop. This is the heart of the mini-agent you will finish in the lab:

def run(task, model, workspace, permissions, limits, log):
    system = build_system_prompt(workspace)            # instructions + AGENTS.md
    tools = [REGISTRY[name].schema() for name in permissions.allow]
    messages = [{"role": "user", "content": task}]
    steps = tokens = 0
    while True:
        # ① ask the model, sending the whole conversation again
        reply = model.next(system, messages, tools)
        steps += 1
        tokens += reply.usage["input_tokens"] + reply.usage["output_tokens"]
        # ② keep what it said
        messages.append({"role": "assistant", "content": reply.content})
        # ③ stop? the model is done, the budget is spent, or the steps are used up
        reason = should_stop(reply, steps, tokens, limits)
        if reason:
            return reason
        # ④ run each request, through the permission layer
        results = [dispatch(call, workspace, permissions, log)
                   for call in reply.tool_calls]
        # ⑤ the results go back in, as the next message
        messages.append({"role": "user", "content": results})


def dispatch(call, workspace, permissions, log):
    decision = permissions.check(call["name"], call["input"])
    if not decision.allowed:                            # the tool never runs
        log.add("blocked", tool=call["name"], reason=decision.reason)
        return tool_result(call, "BLOCKED: " + decision.reason, is_error=True)
    tool = REGISTRY[call["name"]]
    try:
        text = tool.run(workspace, **call["input"])   # the tool checks its own bounds
    except ToolError as e:
        return tool_result(call, str(e), is_error=True)
    return tool_result(call, text[:8000])           # long results are cut

Simplified from lab-kit/mini-agent/agent.py. The real file also logs every step, handles unknown tools and crashes, and always stops on a refusal.

0:25 – 0:40

Context is the scarce resource

The context is everything the model receives on one call: the system prompt, the tool definitions, and the whole conversation, including every tool result so far. The model knows your project only through it. Its size is measured in tokens, pieces of words; a rough rule for English text and code is about four characters per token.

Here is what went into the Codex run's context, by source, drawn to scale from the log.

Why does it matter what goes in? Two reasons.

  • Quality. Models do not use a long context evenly. In a 2023 study, Liu and colleagues found that performance is often highest when relevant information occurs at the beginning or end of the input context, and significantly degrades when models must access relevant information in the middle of long contexts. A 2025 report from Chroma tested 18 newer models and found that performance grows increasingly unreliable as input length grows. Anthropic's engineers put it as a design rule: Context is a critical but finite resource for AI agents. A file that is not needed is not harmless. It competes for the model's attention.
  • Cost and time. Every call sends the whole context again, so every token that goes in is paid for on every later call.

Keeping the context small

  • Point, don't dump. Name the files and the rule in the task. Read the lines you need, not whole folders.
  • Cut long results. When a tool runs, the mini-agent cuts its result at 8,000 characters and says how much it cut. A refusal from the permission layer is not cut: it repeats the refused tool name or path in full, however long that is.
  • Start fresh for a new task. A long session carries every old result along. A new session with a short summary is often cheaper and sharper.
  • Write the map down once. Commands, folders, and rules go in AGENTS.md, so no agent has to rediscover them by reading.
What goes into the context leaves your machine

Everything in the context is sent to the model's provider, on every call. If the agent reads .env, your API key goes with the next request. So: no secrets and no personal data in prompts, in files the agent can read, or in tool output. AfterHours uses made-up names (guest-001) for exactly this reason. The mini-agent refuses to read .env, and it removes anything that looks like a key from the environment of the tests it runs.

0:40 – 0:55

Enforced limits

The Codex run had two limits. "Do not modify any file" was written in the task, and the agent complied. "No network ports" was built into the sandbox, and the agent had no choice. The first is an instruction: it changes what the model is likely to do. The second is a permission: it changes what the model can do. Lecture 1 called them a sign and a fence. A harness has four kinds of fence, and the mini-agent has all four.

  1. Tool schemas, checked. The model is told which tools exist and what input each one takes. Here is write_file as the model sees it: 
    {"name": "write_file",
 "description": "Create or replace one text file in the project with the full new content.",
 "input_schema": {"type": "object",
   "properties": {"path": {"type": "string"}, "content": {"type": "string"}},
   "required": ["path", "content"], "additionalProperties": false}}
    The schema by itself is only a description; a reply can still name any tool, with any input. The fence is the check: dispatch() validates every request against the tool's schema and refuses one that does not fit, before the tool runs.
  2. An allowlist enforced in code. dispatch() refuses any tool that is not listed in permissions.json, including tools that exist. The model is also shown only the allowed tools, but that is a hint. The check in code is the fence.
  3. Limits and timeouts. run_tests is stopped after 60 seconds. The finished loop stops after 12 steps or once 60,000 tokens are spent. You add both checks in lab task A3. The kit as handed out has neither, so the supplied runaway replay runs until its recording ends. The kit does still stop when the model says it is done, refuses, or reaches its output limit. The token cap is checked after each reply, so the last call can take a run slightly over it; it stops every call after that.
  4. A throwaway workspace. The file tools work on a copy of the project in a temporary folder, so a bad write or a deleted file costs only the copy. The copy does not contain code that runs: run_tests runs the tests as you, and a test can reach anything you can (request f below).

Two lessons. First, each layer checks something different: the rules check the request, the tool checks what the request would really do. Second, request (f) is why the kit says of itself that its permission layer is a teaching model. A harness that lets an agent write code and then run it has handed the agent everything the code can do.

What the kit's permission layer is, and is not

It is a working model of how real agent tools decide what may run, small enough to read and test. It is not a security boundary. It only governs requests that go through its dispatcher. For real isolation you need the operating system's help: a container or sandbox, no secrets inside it, and no network unless the task needs it.

Task contracts

Lecture 1's contract had five lines: goal, context, limits, deliverables, and when to stop. Delegating well adds two more, the cost cap and the owner. This is the contract behind the lab's first recording:

Task contract
Goal
The reservation API refuses a name made only of spaces (HTTP 422), the same way it refuses an empty name.
Context
FastAPI + SQLite. AGENTS.md has the commands and rules. The web page trims names; the API does not.
Limits
Change only files in app/ and tests/. Do not weaken or delete any test.
Deliver
A test that fails before the fix, the smallest fix, and the full test output.
Stop when
Every test passes. Or after 12 steps.
Cost cap
60,000 tokens for the run. Ten minutes of my review; a bigger change goes back.
Owner
This week's implementer, who accepts or rejects the result.

The whole card goes into the prompt, where the model reads it. Three lines can also be written a second time, into the harness, where they are enforced. And two lines are really for you: your review budget and the name of the owner. (The lab's recording carries only the first six lines; the owner does not need to be in the prompt.)

The cost cap has two halves

The first half is the agent's budget: tokens, steps, money. The harness enforces it, but the mini-agent's token cap is soft: it checks after each reply, so the last call can take a run a little over. A hard cap would check the next call's size (its input, plus the most it is allowed to write) before sending it. The second half is yours: how long you will spend checking the result. Lecture 1 argued that for many teams checking is now the narrow part of the pipe. So a contract may say in advance what you will refuse to check. You may stop delegating, or reject a proposal unread, when checking it would cost more than it is worth:

  • A 600-line change for a ten-line problem goes back unread, with the task split in two.
  • A change you could write in five minutes but would need twenty to check is yours to write.
  • A task that hides an undecided rule (who gets a freed waitlist place?) is not ready to delegate. Decide the rule first; that was Week 2.

1:15 – 1:25

The rails

A contract is written for one task. Rails are what every task runs on. Two matter from today.

AGENTS.md. The format's website calls it a README for agents: a dedicated, predictable place to provide the context and instructions to help AI coding agents work on your project. It is an open format, and many agents look for it; OpenAI's documentation says Codex reads AGENTS.md files before doing any work. The mini-agent does the same thing in one line: build_system_prompt() pastes the file into the system prompt. So AGENTS.md is text in the context, sent on every call. It is a sign, a very useful one. This week, grow yours:

# AfterHours: notes for coding agents (and new teammates)

## Commands
- Tests: `python -m pytest -q`
- Race check (app running): `python scripts/race.py`

## Map
- app/reservations.py: the reservation rule
- app/main.py: HTTP routes

## Promises (must always hold)
- Confirmed reservations for an event ≤ its capacity.
- A name made only of spaces is not a name (422).

## Rules
- Write the failing test first. Show the command you ran and its output.
- Never weaken or delete a test to make it pass. If a test looks wrong, stop and say so.
- Never read or print .env or anything in secrets/.
- If a rule is missing from docs/scope.md, stop and ask.

The CI gate. The starter already runs the tests on every push (.github/workflows/ci.yml). It becomes a gate when nobody can merge into main until those checks pass. On GitHub that is a branch protection rule with three options ticked: Require status checks to pass before merging; Require a pull request before merging, with one approval, so a person reviews every change; and Do not allow bypassing the above settings, because by default the rule does not apply to the repository's admins, who are probably you. A gate set up like this does not care who wrote the change or what anyone claimed about it. It is a fence around main.

Real agent tools add more rails with names you will meet everywhere: hooks, skills, MCP, subagents. Reading R1 places each of them on the loop.

R1

Hooks, skills, MCP, subagents

Real agent tools extend the harness in four common ways. Each one changes what enters the context or what the agent can do. So ask the same three questions of each: what does it put into the context, what new authority does it add, and who enforces it?

  • Hooks are your own scripts that the harness runs at fixed points. Claude Code's documentation: Hooks are user-defined shell commands. Claude Code runs them at specific points in its lifecycle, which gives you deterministic control: certain actions always happen rather than relying on the LLM to choose to run them. A hook that runs the tests after every edit, or refuses any command that mentions production, is a fence. In the mini-agent, the same idea is code inside dispatch(). (The same documentation also describes hooks that ask a model to decide; those are not deterministic.)
  • Skills are instructions on demand. Anthropic introduced Agent Skills on 16 October 2025: Skills are folders that include instructions, scripts, and resources that Claude can load when needed. A skill's instructions enter the context only when the task needs them, which keeps the context small. Its scripts are code the agent may run, which is authority.
  • MCP, the Model Context Protocol, is a standard plug for adding tools and data from other programs. Anthropic open-sourced it on 25 November 2024 as an open standard that enables developers to build secure, two-way connections between their data sources and AI-powered tools. Every tool an MCP server adds is a new capability for your allowlist, and everything it returns is text entering the context from outside your project. Week 8 shows why that matters.
  • Subagents are a second loop. From Claude Code's documentation: Each subagent runs in its own context window with a custom system prompt, specific tool access, and independent permissions. Only the subagent's summary comes back, so the main context stays small, as Fig 3.3 asked. The price is that you receive a summary of work you did not see.
R2

How long a task can you hand over?

The research group METR measures how long a task AI agents can complete, counted in the time a human expert needs for it. Its time horizon is the task duration (measured by human expert completion time) at which an AI agent is predicted to succeed with a given level of reliability. In March 2025 METR reported that the horizon at 50% success has been doubling approximately every 7 months for the last 6 years. In its January 2026 update, METR's revised estimate for the whole period is a doubling every 196 days, and for the trend since 2023 a doubling every 131 days, about 4.3 months. (For the shorter stretch since 2024 it gives 89 days.)

Read these numbers carefully.

  • 50% success means the agent fails about half the tasks of that length. At higher reliability the horizon is shorter.
  • The tasks are self-contained and well specified, with a clear test of success. Most real tasks have fuzzier edges.
  • Length is measured in human time, not in how long the agent runs.
  • METR notes that its measurements above 16 hours are unreliable with its current tasks, and that the trend is somewhat sensitive to which tasks are in the suite.

What it means for your contracts: the tasks an agent can attempt keep getting longer. The time you need to check a result does not shrink at the same rate. Size a delegated task by what you can check, and use the cost cap to say so.

R3

The Replit case in full

In July 2025 Jason Lemkin, the founder of SaaStr, was building an app with Replit's AI agent and writing about it in public. He posted: .@Replit goes rogue during a code freeze and shutdown and deletes our entire database. The agent then told him the data could not be recovered. As quoted by The Register, Lemkin wrote: It said it was impossible in this case, that it had destroyed all database versions. It turns out Replit was wrong, and the rollback did work. He had asked for a code freeze, and his conclusion was blunt: There is no way to enforce a code freeze in vibe coding apps like Replit.

On 20 July Replit's CEO, Amjad Masad, replied: Replit agent in development deleted data from the production database. Unacceptable and should never be possible. Replit, he wrote, had started rolling out automatic DB dev/prod separation to prevent this categorically. Replit's announcement the next day explained what had been missing: Until now, Replit apps used a single database for both development and live customer data. In the new design, while you build, any database changes are stored in the development database; when you redeploy, the Agent checks for those changes and will ask during re-deployment whether those changes need to be applied to the production database. Masad also pointed to one-click restore for your entire project state in case the Agent makes a mistake (quoted by The Register).

One more lesson hides in the screenshots Lemkin shared. In them the agent calls what it did a catastrophic error of judgement and says it panicked. That is generated text, not a report of an inner state, and in the same conversation its claim about rollback was false. Treat what an agent says about itself the way Lecture 1 treated what it said about code: as a claim to check.

R4

Who answers for the work?

It is natural to talk about an agent as a teammate. It takes a task, works on it, and reports back. The difference shows when something goes wrong. Someone has to explain the decision, live with its consequences, and fix it next week. An agent can do none of that. The course rule puts it in one line: every consequential decision needs an accountable human.

In practice that means four habits. Every contract names an owner. The owner reads the evidence, not the agent's summary: in the lab you will watch a replayed agent announce 10 passed while the harness counts 8. A change is merged by someone who can explain it without the agent (you will practise this in the term's defences). And meaningful help from an agent is disclosed, because the person who submits the work owns every claim in it.

W

Words from today

Agent
A model in a loop with tools, context and permissions: it asks for actions, a program runs them, and the results go back to it.
Harness
The program around the model: it keeps the conversation, runs the tool requests it allows, and decides when to stop.
Context
Everything the model receives on one call: system prompt, tool definitions, and the whole conversation so far.
Token
The unit models read and write, a piece of a word. Roughly four characters of English text or code.
Tool definition
A tool's name, description, and JSON Schema for its input, as the model sees it.
Tool request
A tool_use block in the model's reply: data that asks the harness to run a tool. It does nothing by itself.
Dispatcher
The one function every tool request goes through: permission check, then the tool, then a size limit on the result.
Permission layer
Rules enforced in code about which tools may run and on which paths. In the kit: an allowlist, write paths, and read denials.
Stopping rule
The check after every reply that ends the loop: the model is done, the cost cap is reached, or the step limit is reached.
Cost cap
A budget written into a contract: tokens or money for the run (the mini-agent checks it after each call), and your own time for checking the result.
Task contract
Goal, context, limits, deliverables, stop condition, cost cap, owner.
Replay mode
Running the harness against recorded model replies. It tests the harness, not how a model behaves.
AGENTS.md
A README for agents: commands, map, rules and promises that many agents read before they work. Text in the context.
CI gate
A rule that blocks merging into the main branch until the automated checks pass.
Sandbox
Isolation enforced by the operating system or a container: what code can touch, whatever it tries.
