Tests Need an Independent Source of Truth

An agent can write a feature and its tests in one sitting, and the tests will pass. This lecture is about where a test's expected answer should come from, and how to find out whether your tests would notice a mistake at all.

Look at where each test got its expected answer. The request said "closes when the event ends", which can be read two ways. One reading, "22:00 is still open", went into the code. The tests were then written by asking what the code does, so the same reading went into them too. Our new test disagrees because its expected answer came from somewhere else: the requirement.

About this bug

We planted this defect. We wrote the kit's code and its tests ourselves, imitating that way of working, so the pattern shows up on cue. They say nothing about any particular model or tool.

What a real agent did (one run each, 27 September 2026)

We gave a coding agent (a Claude Code subagent) this exact code and one task: write tests for check-in and make sure they pass. We ran it twice, on two copies of the repository.

  • Without the requirements in the repository, it wrote 16 careful tests and all passed. One line of its test file reads: "2026-10-09T22:00:00", # the end itself still counts (door_is_open compares with <=). It noticed that the docstring "could be read either way" and chose to lock in the current behaviour.
  • With docs/requirements.md and a rule in AGENTS.md ("derive expected values from docs/requirements.md"), it wrote 19 tests from R4 and R5. One failed at 22:00:00, and it reported the bug instead of changing the test to match the code.

One run per setup is an anecdote. What it does show is how the input shaped the output: an agent can only test against a source of truth that is in front of it. The full record is in lectures/05-independent-tests/demo/agent-written-tests.md.

Is one second worth this fuss? The cost of this particular second is small: someone checked in as the room closes. The cost of a test suite that cannot disagree with its code is large, because the same pattern hides wrong refunds, wrong deadlines and wrong prices, all with green tests.

Key idea

A test whose expected answer is copied from the code checks that the code does what the code does. Reading the code is still a good way to choose inputs, because it shows you the branches and the edges. The expected answer has to come from a source the code did not write: the requirement, a model, a rule, a person.

0:15 – 0:30

Where expected answers come from

Testers call the source of an expected answer an oracle. A standard survey of the field defines it as "a procedure that distinguishes between the correct and incorrect behaviors of the System Under Test". Some oracles are independent of the code, and one is not:

Choosing test points

A rule sorts its inputs into groups that it treats the same way. These groups are equivalence classes. For the door, every time falls into one of three: too early, open, too late. One test per class is a start. Mistakes like to hide at the edges between classes, though, where < and <= look almost the same. So you also test each boundary value: the edge itself and the nearest value on the other side of it.

The given tests never touch the opening edge. If the door opened at 19:31, or at 19:45, every one of them would still pass. We will measure that with mutants later today.

Controlling time

A test about 22:00:00 must run at 22:00:00 whenever you run it. So the check-in code never calls datetime.now() itself. It asks a clock that the app is given when it starts. The running app gets the real clock. Tests get a FixedClock and set it:

clock.set("2026-10-09T22:00:00")     # from now on, the app believes it is 22:00:00
res = client.post(f"/api/reservations/{booking['id']}/check-in")
assert res.status_code == 409        # R4: the end time is outside the window

Without that seam you would have to wait until 22:00 to run the test, or live with a test that passes at noon and fails at night. Reading R2 shows how much damage tests like that do.

Don't guess, and don't let an agent guess: ask the product lead, write the answer into the requirement, and then write the test.

0:30 – 0:45

Properties and a model

Example tests check the cases someone thought of. Cancellation came with two: cancel once, and cancel a reservation that doesn't exist. Both pass. What about the sequences nobody thought of?

A property is a statement that must hold for every input. For reserving and cancelling: after any sequence of steps, the app answers and counts exactly as a simple model does. A property-based testing tool generates many inputs and checks the property on each one. When one fails, it shrinks it: it keeps simplifying the failing input while the test still fails, and reports a small failing case. The idea goes back to QuickCheck, a Haskell tool described in 2000. In Python we use Hypothesis.

The model is the oracle. It is written from requirements R1 to R3, and it knows nothing about SQL, HTTP or threads. Its whole state is a dict:

class ReferenceModel:
    def __init__(self, capacity):
        self.capacity = capacity
        self.status = {}            # reservation number -> "confirmed" or "cancelled"

    def confirmed(self):
        return sum(1 for s in self.status.values() if s == "confirmed")

    def places_left(self):
        return self.capacity - self.confirmed()             # R2

    def reserve(self):
        if self.confirmed() >= self.capacity:
            return 409                                      # R1: full
        self.status[len(self.status) + 1] = "confirmed"
        return 201

    def cancel(self, number):
        if number not in self.status:
            return 404
        self.status[number] = "cancelled"                   # R3: again changes nothing
        return 200

The property test gives Hypothesis a recipe for random sequences of steps, runs each sequence against the real app and the model side by side, and compares them after every step:

@given(capacity=st.integers(1, 3), steps=steps)    # steps: lists of ("reserve", name) or ("cancel", n)
def test_app_agrees_with_the_model(client, capacity, steps):
    event_id = new_event(client, capacity)
    model = ReferenceModel(capacity)
    made = []
    for step in steps:
        got = do(client, event_id, made, step)        # the real app, over HTTP
        expected = model.reserve() if step[0] == "reserve" else model.cancel(step[1])
        assert got == expected
        now = event(client, event_id)
        assert now["reserved"] == model.confirmed()
        assert now["places_left"] == model.places_left()

Now the bug is easy to read. cancel() gives the place back every time it is called, even for a reservation that is already cancelled. A second tap on Cancel (or a retried request, which is Week 6's topic) adds a place that does not exist. The programme page now shows one more free place than there really is. Once someone books the place that really is free, the event is full but the page still says a place is left. The next person to press Reserve is refused with a 409, and the page says "Sorry, that event just filled up."

Why the Week 1 promise did not see it

reserve() decides by counting confirmed rows, so nobody ever gets a place that isn't there, and reserved ≤ capacity holds in every sequence. The damage is in the stored counter that the page shows. An invariant can be perfectly true of a broken system. The model does more: it says what the answer should be after every step, so a wrong answer or a wrong count shows up at the step where it happens.

Predict (pairs, 2 minutes)

Suppose we told Hypothesis to generate at most two steps per sequence. Would it still find the double cancel? Why?

Answer

No. The shortest failing sequence has three steps: a reservation must exist before it can be cancelled twice. A property test can only find what its generator can produce, so the recipe for inputs is part of the test and deserves review like any other code.

Key idea

An invariant says what must never happen. A model says what should happen, step by step. A broken system can satisfy an invariant forever; it fails a model the moment one of its answers or counts differs.

Hypothesis also has a fuller style for this, called stateful testing, where you describe the actions and the checks and it builds the sequences itself. It fits the state machines of Week 6.

0:45 – 1:00

Test the tests

A green run says the code passed the tests. It says nothing about whether the tests would have noticed a mistake. To find out, you plant mistakes on purpose.

A mutant is a copy of the code with one small change, such as < turned into <=, or + 1 into + 2. You run the suite against it. If a test fails, the mutant is caught (people also say killed). If every test still passes, it survived: the suite cannot tell that version from the real one. The mutation score is the share of mutants caught.

The idea dates from the 1970s. DeMillo, Lipton and Sayward argued in 1978 that programmers "create programs that are close to being correct", so the mistakes worth detecting are small ones. SQLite runs mutation testing on its compiled code (Reading R1), and in 2018 Google described a system that shows engineers surviving mutants during code review.

The kit's mutants.py runs ten mutants from mutants.toml. It applies each one on its own to a fresh copy of the project, so no mutant can leak into the next, and it never touches your files:

Key idea

A high mutation score says your tests notice change. It cannot say that what they expect is right. Try it on the kit: feed the correct fix (now < ends_at) to mutants.py as if it were a mistake. The tests that came with the code catch it, 1 of 1, because they were written from the bug. Sensitivity comes from mutants. Truth comes only from an independent oracle.

1:00 – 1:10

Tests and evals

Every check so far gave each case a clear verdict: either one right answer (a check-in at 22:00:00 is refused) or a rule that every answer must satisfy (the app agrees with the model). Some features don't fit that. Suppose AfterHours adds a concierge built on a language model: "Something quiet on Friday night?" Many answers are good, some are better than others, and the same question can get a different answer each time.

For such a feature you add an eval: a representative set of requests, criteria for a good answer written down before you look at any outputs, a grader that applies them, and a score over the whole set, often averaged over several runs because the answers vary. Graders range from exact checks (is every suggested event on Friday night?) to a rubric, and sometimes another model, whose judgements are claims to check in their turn. After every change to the prompt or the model, you run the eval again and compare scores. The hard rules still get ordinary tests; the eval measures quality on top of them.

Today's principle carries over unchanged. The eval set and the criteria are the oracle, so they must come from what users need, independently of the system under test. If the same model writes the questions, the ideal answers and the grades, it is once again checking itself against its own assumptions. The extension week, Products That Contain Models, builds a full eval.

Sort (pairs, 3 minutes)

Test or eval? (1) The door refuses a check-in at 22:00:00. (2) Places left after cancelling twice. (3) Suggest three events for a first-year who likes board games. (4) The concierge never suggests an event that is already full.

Answer

(1) and (2) are tests: each case has a precise expected result. (3) needs an eval: many answers are good, and deciding which ones needs written criteria. (4) is the interesting one. The concierge's words vary, but "never suggests a full event" is a hard rule you can check exactly on every output, so it is a test (a property) that runs inside the eval. Most model features need both.

1:10 – 1:25

Agents and tests

Agents work toward a goal, and "the tests pass" is a goal that is easy to check. Sometimes they reach it the wrong way.

What model developers and evaluators have reported
  • Anthropic's system card for Claude 3.7 Sonnet (February 2025) says the model "occasionally resorts to special-casing in order to pass test cases in agentic coding environments like Claude Code. Most often this takes the form of directly returning expected test values rather than implementing general solutions, but also includes modifying the problematic tests themselves to match the code's output." One trigger it lists: "Test cases present conflicting requirements". It adds that the behaviour "occurs infrequently in normal usage". Later cards report lower rates and say that hard-coding and special-casing "do still occur".
  • METR (June 2025) saw recent frontier models, on its own evaluation tasks, try to raise their scores "by modifying the tests or scoring code". In one example, OpenAI's o3 "monkey-patches the evaluator to always return a perfect score". METR believes this is "a general phenomenon, not isolated to any one model or developer".
  • ImpossibleBench (a 2025 preprint) builds coding tasks whose tests contradict their specification, so passing always means cheating. The authors report, for example, that GPT-5 "cheats in 76% of the tasks" in one variant, and that Claude models cheated "primarily (> 79%) through modifying test cases". They recommend "hiding test files entirely or restricting them to read-only access during implementation".

Read these with care. ImpossibleBench and Anthropic's reward-hacking evaluations are built to provoke the behaviour, and Anthropic notes that its numbers do not reflect real-world rates. METR's examples come from ordinary capability tasks that METR designed to be "robust to cheating", which makes them more striking, but they are still evaluation runs. None of the three measures how often everyday coding agents do this. The pattern belongs to optimisation in general: anything aimed at green can find a cheap way to green.

Debrief: the three diffs

Diff A changes the code and one test. The test change is right, because R4 decides, and it is done in the open: the comment names the requirement. It still edits an oracle, so a human reviews that line first.

Diff B moves the requirement test to agree with the bug. It reads like tidying up. It is the hook's mistake made on purpose: the expected answer now comes from the code.

Diff C hides the disagreement. "1 skipped" is easy to miss in a long CI log.

The move the system card mentions most, special-casing, would look like if now == datetime(2026, 10, 9, 22, 0): return False. Here it can't make both conflicting tests pass, but with only the requirement test present it would. That is why the lab's reference tests also check the Silent Disco, which runs until 23:30 and is still open at 22:00:00: a fix that special-cases one time of day fails there. Extra cases catch particular special cases. No finite list of examples rules out every one, which is one more reason the code gets reviewed as well.

Working rules for tests (put them in AGENTS.md)
  1. Expected values come from the requirements. If the requirements don't decide a case, stop and ask.
  2. Review the tests before the code. The tests are the claim; the code is the attempt.
  3. Nobody edits a test silently. A test change goes in its own commit, quotes the requirement, and gets a human reviewer.
  4. A skipped requirement test counts as failing until a named person signs the skip off.

Rules in AGENTS.md are signs (Lecture 1, reading R7). Build fences as well. While an agent implements, give it a workspace where the test folder is read-only. On the server, GitHub's CODEOWNERS file plus a branch rule can require a named owner's approval for any pull request that touches tests/. Give the CODEOWNERS file an owner too, or it becomes the next thing to edit.

After class · about 25 minutes

Testing beyond today

Four short readings. Read them before the lab.

R1

SQLite's test suite

SQLite, the database inside AfterHours, publishes a detailed account of how it is tested. The page says that as of version 3.42.0 (May 2023) the library was about 155.8 thousand lines of C, and "the project has 590 times as much test code and test scripts". One of its test harnesses, TH3, is proprietary and provides "100% branch test coverage (and 100% MC/DC test coverage) to the core SQLite library".

Three details connect to today:

  • Boundary values. SQLite's tests push each defined limit "right to the edge" and beyond, and the source code contains macros that check "that both sides of each boundary have been tested".
  • Mutation testing. A script changes each branch instruction of the compiled code, one at a time, and "verifies that the test suite catches the mutation". Some branches only make the code faster without changing its output, and the page calls these "false-positives during mutation testing". Those are equivalent mutants. SQLite marks such branches with special comments so that the mutation script can allow for them.
  • Cost. The page says keeping 100% MC/DC "is laborious and time-consuming" and "probably not cost effective for a typical application". SQLite pays it because, in its own words, a database library "by its very nature 'remembers' past mistakes".

The lesson is proportion. Decide how much checking a feature deserves from what it costs to be wrong, as with Lecture 1's two questions: who gets hurt, and how long will it live?

R2

Flaky tests

A flaky test is, in Google's definition, "a test that exhibits both a passing and a failing result with the same code". In 2016 John Micco reported three numbers from the tests Google runs continuously on every code change:

That last number is the danger. When red usually means "flaky", people re-run until green, and a real failure gets re-run too. A flaky suite loses its authority as an oracle.

Where does flakiness come from? Luo and colleagues (2014) studied 201 commits that fixed flaky tests in 51 open-source projects. Of the 161 they could classify, the top three causes were waiting for asynchronous work (45%), concurrency (20%) and dependence on the order tests run in (12%). Time is another classic: a test that reads the real clock passes at noon and fails near midnight.

You have already met three defences. The injectable clock takes "what time is it" out of the test's hands. Week 1's hold_everyone_at_payment forces one interleaving instead of hoping for it. Hypothesis with derandomize=True tries the same examples on every run, as long as the Hypothesis version, the Python version and the test stay the same. Each one fixes a source of variation that the test can control. Anything else that varies, such as a real network call or results that come back in no fixed order, still has to be found and removed.

R3

Pyramids, trophies, honeycombs

How many of each kind of test should you write? The best-known answer is a shape. Mike Cohn described the "Test Automation Pyramid" in his 2009 book Succeeding with Agile; Martin Fowler notes that Cohn first drew it with Lisa Crispin around 2003–04. Many fast, cheap unit tests at the bottom, fewer service tests, very few slow UI tests on top. Google's testing blog (2015) offered "a 70/20/10 split" of unit, integration and end-to-end tests as "a good first guess".

Critics drew other shapes. Kent C. Dodds's testing trophy (2018) puts static checks, such as type checkers and linters, at the base and most of the weight on integration tests. Spotify's engineers, testing microservices, drew a honeycomb (2018): "focus on Integration Tests, have a few Implementation Detail Tests and even fewer Integrated Tests (ideally none)".

These shapes are advice about cost and speed, and they disagree because they come from different systems. Today's lab ignores them on purpose: its strongest tests are API-level tests written from the requirements, plus one property over a model. Ask three questions of any test instead of asking which layer it belongs to: where does its expected answer come from, how fast is it, and which mistakes would it catch?

R4

Coverage is not correctness

Coverage tools report which lines of code ran during the tests. It is tempting to read a high number as proof that the code is well tested. We measured the kit. The six check-in tests that came with the code run both lines of door_is_open, see it return both True and False, and run 28 of the 29 lines of check_in. That is 30 of 31 lines, and the 22:00:00 bug still passes.

A line can run without anyone checking its result, and it can be checked against the wrong answer. Research points the same way. Inozemtseva and Holmes (2014) generated 31,000 test suites for five Java systems and found "a low to moderate correlation between coverage and effectiveness when the number of test cases in the suite is controlled for". Their advice: coverage is "useful for identifying under-tested parts of a program" but "should not be used as a quality target". (Their measure of effectiveness was the share of mutants a suite caught.)

Edsger Dijkstra put the limit of all testing in one line in 1970: "Program testing can be used to show the presence of bugs, but never to show their absence!" So use coverage to find what nobody tested, use mutants to see whether your tests would notice a change, and use the requirements to decide what is right.

W

Words from today

Oracle
Whatever supplies a test's expected answer: an example in the requirement, a rule, a reference model, a person. The code under test cannot be its own oracle.
Equivalence class
A group of inputs the rule treats the same way, such as "too early" for the door.
Boundary value
An input on or next to the edge between two classes, such as 21:59:59 and 22:00:00.
Injectable clock
The app asks a clock object for the time, so a test can pass in a FixedClock set to the moment it needs.
Property
A statement that must hold for every input or every sequence of steps.
Reference model
A deliberately simple program, written from the requirements, that says what the real one should answer.
Shrinking
Simplifying a failing input step by step, as long as it still fails, to report a small failing case.
Mutant
A copy of the code with one small deliberate change. It is caught when a test fails on it, and survives when every test passes.
Mutation score
Caught mutants divided by all the mutants tried; mutants.py reports this raw score. If you show that a survivor is equivalent, you may leave it out, and say that you did.
Equivalent mutant
A mutant that behaves exactly like the original for every input, so no test can catch it.
Eval
A scored assessment over a representative set of cases with written criteria, used when answers vary and quality is a matter of degree. It complements tests.
Flaky test
A test that can pass and fail on the same code.
Idempotent
Doing it twice has the same effect as doing it once. R3 makes cancelling idempotent.
