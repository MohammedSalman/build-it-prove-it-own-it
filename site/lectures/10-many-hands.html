Week 10 · Parallel work, with people and agents

Many Hands, One System

Two teammates each handed a task to a coding agent. Both branches passed every test, git merged them without a single conflict, and the festival programme moved every event two hours earlier. This lecture is about why more hands, human or agent, need explicit agreements where their work meets, and how to split work so those meeting points are few and guarded.

90-minute lecture 2-hour lab ~30 minutes of reading after class Loop: Delegate Kit: one repository, two branches, one bundle

By the end of today you can

  • Explain how two green branches can merge without a conflict and still break the system.
  • Count possible communication channels with n(n − 1)/2, and say what that number does and does not measure.
  • State Conway's law in Conway's own words, and predict where a split of the work will put the system's interfaces.
  • Split work by dependency, find the critical path, and give parallel agents their own git worktrees.
  • Write an integration contract with examples, test both sides of a boundary against it, and run CI on the merged result.
  • Choose an orchestration pattern for agents, and say when not to parallelise at all.

On Friday at 19:00, Maya opens the programme. The escape room starts at 20:00 and has one place left, but the programme lists it at 18:00 and marks it Started, so the page greys out its Reserve button. Every other event is listed two hours early too. Maya closes the app, and the last place stays empty.

About this bug

We planted this conflict on purpose and wrote both branches ourselves, in the way agent work often looks. Ana, Ben and Priya are fictional. The example says nothing about any particular model or tool. The pattern itself is common: two parts of a system disagree about what one shared value means, and each part's tests encode its own belief. Week 4's Mars Climate Orbiter had the same shape, with units instead of time zones.

Agent-off drill (5 minutes, no laptop, pairs)

Trace one value by hand. The organiser types the escape room's start as printed on the poster, 2026-10-09T20:00. Follow it through the merged code. Festival time is UTC+2.

# Ana's branch, app/festival.py: this WRITES starts_at
def to_utc(text):
    moment = datetime.fromisoformat(text)             # 20:00, no zone attached
    if moment.tzinfo is None:

    return moment.astimezone(timezone.utc).strftime("%Y-%m-%dT%H:%M:%SZ")

# Ben's branch, app/programme.py: this READS starts_at
def festival_start(starts_at):
    # starts_at is stored as festival local time (see app/schema.sql)
    return datetime.fromisoformat(starts_at).replace(tzinfo=FESTIVAL_TZ)

  1. What string does Ana's code store?
  2. What does Ben's code turn it into, and what hour does the programme print?
  3. At 19:00 festival time, does the programme say Started? Does the server, whose closing rule Ana updated to read UTC, still accept a booking?
  4. Which branch is wrong?
Answers: one value, two meanings (open after the drill)
  1. Ana stores 2026-10-09T18:00:00Z. 20:00 at UTC+2 is 18:00 in UTC.
  2. Ben's code reads 18:00 UTC, keeps the reading 18:00, and relabels it as festival time. That instant is 16:00 UTC, two hours before the real start. The programme prints Fri 9 Oct · 18:00.
  3. At 19:00 the programme compares 19:00 with its wrong 18:00 and says Started. The server compares 17:00 UTC with 18:00 UTC and accepts the booking. The page and the server now disagree about when the event starts.
  4. Neither, on its own. Ben's comment was true when he branched: on main, starts_at held festival time, and his line copies the closing rule's conversion exactly. Ana updated every reader of starts_at that existed on main, the closing rule included. Ben's reader did not exist yet. It was being written at the same time, in another folder.
Key idea

Git merges lines of text. Nothing merged the meaning of starts_at. When two changes are right alone and wrong together, the bug lives in the agreement between them. Here there was no written agreement, only a comment in schema.sql that one branch changed and the other believed.

Why did every test stay green? Each branch's tests encode that branch's belief. Ben's unit tests feed his code strings he typed himself, in the format he expected ("2026-10-09T20:00"). His one test through the API checks the order of events and a status on Saturday afternoon, hours away from any start time. Ana's tests check what is stored and served. No test crossed the boundary from what the organiser types to what the programme shows. That test is an integration test. On Ben's branch alone it passes. It can catch this bug only where both changes exist, on the merged build. You write it in the lab.

0:15 – 0:30

Brooks's law and communication paths

When a project falls behind, the instinctive fix is more hands. Today that can mean a few more agents, started in a minute. The classic warning about this instinct is more than fifty years old. In 1964 Fred Brooks became manager of IBM's Operating System/360, a project that at its peak had over 1000 people working on it. In 1975 he drew the lessons in The Mythical Man-Month. (The book's language is of its time; its argument is about people and agents alike.)

Its second chapter attacks the idea that people and months can be traded one for one. Men and months are interchangeable commodities only when a task can be partitioned among many workers with no communication among them, like reaping wheat. When steps must happen in order, extra hands do nothing: The bearing of a child takes nine months, no matter how many women are assigned.

Then he counted the cost of talking. New workers must be trained: Each worker must be trained in the technology, the goals of the effort, the overall strategy, and the plan of work. And coordination grows faster than the team: Intercommunication is worse. If each part of the task must be separately coordinated with each other part, the effort increases as n(n-1)/2. Three workers require three times as much pairwise intercommunication as two; four require six times as much as two. From this he drew his famous law, and labelled it himself: Oversimplifying outrageously, we state Brooks's Law: Adding manpower to a late software project makes it later.

Try it (2 minutes, pairs)

Priya's team is four people, and this week two of them each ran one agent: six contributors. How many possible pairs is that? Now look back at the hook. Which decision had to be shared between the two lanes of work, and was it ever agreed?

What the formula counts, and what it doesn't

n(n − 1)/2 is the number of pairs among n contributors: each can pair with n − 1 others, and that counts every pair twice. It is a count of possible channels. It is not a measured cost, for three reasons.

  • Most pairs never need to talk. The cost comes from the pairs whose work shares a decision. In the hook, six contributors make 15 possible pairs, but what mattered was one decision shared by two lanes (Ana with her agent, Ben with his): the meaning of starts_at. Nobody in either lane talked to the other lane about it.
  • Structure changes the count. If everyone talks through one hub (a lead, a planner), there are only n − 1 channels, but the hub becomes the bottleneck. A written contract that everyone reads replaces many pairwise conversations with one document.
  • Channels differ in price. A two-minute question before work starts is cheap. The same misunderstanding found after the merge costs a debugging session, and on Friday it costs a festival guest.

Brooks knew his law was rough; he said so in the sentence that states it. Twenty years later he reviewed studies of it (reading R1). Treat it as a warning about a common instinct, not as a formula for your schedule.

Does any of this apply to agents?

That is a question to examine, not a law to apply. Here is how each of Brooks's costs might look when the extra hands are agents, and how you could check it for your own team.

One data point, with its limits. In June 2025 Anthropic described its own multi-agent research system: a lead agent that starts parallel subagents. It is a reason to measure parallel agents on your own work, not evidence about your team.

Key idea

n(n − 1)/2 counts who could talk. The cost comes from who must agree. Split the work so that few pairs must agree, and write down what they agree on.

0:30 – 0:45

Conway's law, with agents

In Week 4 you met Melvin Conway's observation from 1968. Here it is again, in his words: organizations which design systems (in the broad sense used here) are constrained to produce designs which are copies of the communication structures of these organizations. Fred Brooks named it Conway's law in The Mythical Man-Month. The same paper counts communication paths seven years before Brooks did: the number of possible communication paths in an organization is approximately half the square of the number of people in the organization.

Two more sentences from that paper matter this week. The first is about the moment you split the work: the very act of organizing a design team means that certain design decisions have already been made, explicitly or otherwise. The second is Conway's advice: a design effort should be organized according to the need for communication.

Now read the hook with Conway's eyes. Priya's two task cards were an organisation chart: one lane for storage, one lane for the page, and no line between them. The code copied it. Ana's module writes starts_at, Ben's module reads it, and the one thing both depend on sat in the gap between the lanes, with no owner.

With agents, this gets sharper. People who share a room overhear each other. Agents in separate worktrees share nothing except the repository and what you wrote for them, so the plan you write is the communication structure. Two consequences:

  • Split along the boundaries you want the system to have. Priya split by layer (storage, page), and one field ran through both layers while Ana's task changed its meaning. Deciding that meaning first, and naming its owner, would have put the agreement on paper before anyone coded.
  • Wherever two lanes meet, put the meeting in writing: an owner, a contract, a test on each side. That is 1:00.

Is Conway's law true? It is an observation, not a theorem. Conway recalls that the Harvard Business Review rejected his paper on the grounds that I had not proved my thesis. Later research found support for a version of it. In a 2012 study of matched pairs of products, MacCormack, Baldwin and Rusnak report that the product developed by the loosely coupled organization is significantly more modular than the product from the tightly coupled organization, in every pair they examined. That is strong evidence for a tendency in their sample of products. We know of no such measurement for teams of agents; you now have one small example of your own.

Try it (3 minutes, pairs)

Think of your team's product. Name two parts of the code that two different people, or agents, will change in the next two weeks. Where do those parts meet: a field, an endpoint, a rule? Who owns that meeting point? If the answer is "nobody", write one sentence that would fix its meaning.

Key idea

The plan is the org chart. When you split work between agents, you are designing the system's interfaces, whether or not you mean to.

0:45 – 1:00

Decompose by dependency

Two tasks can safely run in parallel only if neither needs a decision the other one makes. Touching different code is not enough: Ana and Ben changed different files, and different lines of the one file they both edited (app/main.py), yet one decision, what starts_at means, ran through both. So before you split work between people or agents, draw what depends on what. Three rules of thumb:

  1. Shared decisions first. Decide, and write down, anything two tasks both depend on before either starts. Then each task depends on the decision, not on the other task.
  2. The critical path sets the pace. The longest chain of tasks that must happen one after another is the earliest you can finish, however many hands you add. Brooks's nine months is a critical path of one step.
  3. Keep hot spots in one lane. Two tasks that change the same function or the same data are one task, or two tasks in a row.

  2. 16 hours with one worker, 12 with two, and still 12 with four. A second worker helps; a third and fourth only wait.
  3. With C first, 17 hours of work, and the critical path is C → T4 → T6 = 7 hours. Two workers finish in 10 hours, three in 8, four in 7. The contract costs an hour and makes the graph wide, and a wide graph is what extra hands need.
  4. It did not remove T6, the task that joins everything, or the risk that someone builds against the contract wrongly. The contract moves the integration risk into one known place and gives it tests. That is the next section.

Worktrees: one place to work per worker

Once tasks are independent, each worker needs its own place to work. For agents on one machine, that place is a git worktree. Git's documentation: A git repository can support multiple working trees, allowing you to check out more than one branch at a time. Each worktree is a folder with its own branch and its own files, and all of them share one history. Coding-agent tools build on this; Claude Code's documentation, for example, describes running each session in its own worktree so that edits in one session never touch files in another.

git worktree add ../ah-utc feature/utc-storage        # a folder for Ana's agent
git worktree add ../ah-display feature/local-display  # a folder for Ben's agent
git worktree add -b integration ../ah-merge main      # where the two meet
git worktree list

What worktrees isolate, and what they don't:

  • Separate: the files, the checked-out branch, and untracked files such as each folder's afterhours.db. Git refuses to check out one branch in two worktrees at once.
  • Shared: the history (a commit made in one folder is visible from all of them) and the machine: ports, CPU, anything outside the folder. That is why parallel agents on one machine each need their own scratch folder and their own range of ports.
  • Not separated at all: decisions. Worktrees kept Ana's and Ben's working files apart while they worked; they do not prevent conflicts when the branches merge. This merge was clean only because the two changes happened not to touch the same lines, and nothing in git, or in the worktrees, knew that both depended on what starts_at means.
1:00 – 1:15

Contracts first

An integration contract is a short, owned document that fixes what a shared thing means, with examples that the tests on both sides use. The shared thing can be a database field, an API response, a file format, or a rule. For AfterHours's start times it needs five parts:

  • Representation. Field name, type, format, unit, time zone. Here: a UTC instant, written 2026-10-09T18:00:00Z.
  • One place converts. One module, or one shared type, does every conversion. Nobody else converts, so nobody else can convert differently.
  • Examples. A few rows of input and expected output, including an awkward one: here, an event after midnight, whose UTC date is the day before.
  • Strict readers. A stored or served value that breaks the rule raises an error. Nothing guesses which zone was meant. (Input is different: the organiser's offset-free 20:00 is accepted at exactly one boundary, where it is defined to mean festival time.) Had Ben's reader refused any value that didn't look the way he expected, the merged build would have failed loudly, in his own tests, instead of printing the wrong hour quietly.
  • An owner and a way to change it. One named person. Changes go through a pull request that both sides review, and code that breaks the examples does not merge.

Test both sides against the same rows

A contract that nothing checks decays into a comment, like the one in schema.sql. So each side of the boundary gets a contract test that reads the contract's examples:

  • Producer test (Ana's side): for each row, POST the typed time; the API must store and serve exactly the row's UTC text.
  • Consumer test (Ben's side): for each row, feed the programme the row's served text; it must show exactly the row's label. Not strings typed from memory: the contract's rows.

The difference from Ben's original tests is where the test data comes from. His tests fed his code what he believed starts_at looked like. A consumer test feeds it what the contract says, and the producer test checks that the producer really emits that. If either side drifts, one of them fails.

That is something the integration test alone could not tell you. The integration test says "the system is wrong"; the contract tests say "Ben's side reads the field wrongly". The repair is then small, and it follows the contract: a to_festival function in app/festival.py, the one place that converts, which reads the text strictly as UTC and converts it with astimezone; and one line in app/programme.py that calls it. Run the whole suite after that change, and three of Ben's own tests fail. They were written against his old belief about the format, so they get updated to use the contract's rows, keeping their boundary check. Then everything passes.

CI on the merged result

Contract tests catch a side that drifts from the contract. The integration test catches what the contract forgot. Both only help if they run where the changes meet. On GitHub, a workflow triggered by a pull request checks out, by default, a test merge of the branch into its base. GitHub's documentation puts it plainly: Your CI tests run against the merged result, not just the head branch alone. (A workflow can be written to check out the branch itself instead, so look at what yours does.) And that merge is made with main as it was when the checks ran. Ben's checks ran before Ana's branch landed, so they tested a main without UTC storage, and they stayed green after main changed.

Two repository settings close that gap. Require branches to be up to date before merging makes a branch re-test on the latest main before it may merge. A merge queue does the same for you, one change after another (reading R3). Neither helps if no test crosses the boundary: re-run on top of Ana's change, all 21 existing tests still pass. The queue guarantees that the tests run on the merged result. You still have to write the test that fails there.

Key idea

A contract turns a silent semantic conflict into a failing test, on the side that broke it. CI has to run that test on the merged result, against the latest main.

1:15 – 1:25

Orchestration patterns

Coding-agent tools now let one person run several agents at once. Three roles cover most setups, and each can be filled by a person or by an agent.

  • Planner and workers. A planner splits the work, writes one task card per worker, and brings the results together. Anthropic's guide Building effective agents (December 2024) calls this pattern orchestrator-workers: a central LLM dynamically breaks down tasks, delegates them to worker LLMs, and synthesizes their results. In a repository, each worker gets its own worktree and branch, and the results meet on one integration branch.
  • Reviewer. A second agent, with a fresh context, reviews each change against its task card and the contract before a person does. Because it starts without the author's conversation, it is less likely to share the author's assumptions, so it tends to catch different mistakes. Its review is a signal, not a verdict (Week 7). The same guide describes a related loop, evaluator-optimizer, in which one LLM call generates a response while another provides evaluation and feedback in a loop.
  • A person at the integration point. Whoever merges owns the result. The course rule applies: every consequential decision needs an accountable human.

When not to parallelise

Parallel agents multiply output, and they multiply the places where work must meet. Keep the work in one lane when:

  • A shared decision is still open. Decide it first, or keep the work together. Walden Yan of Cognition, writing about agent systems in June 2025, put it as a principle: Actions carry implicit decisions, and conflicting decisions carry bad results. Ben's one line of code was an implicit decision about starts_at.
  • The design is not settled. Explore with one agent, or one person, and split once the boundaries are clear.
  • The pieces touch the same hot spot. Two agents in one function will conflict in the text, or worse, in the meaning.
  • The task is small. Two task cards and a contract can cost more than doing the work.
  • Review is already the bottleneck. Four agents make four diffs, and someone has to read them.

Anthropic's post about its research system makes the same point from its own experience: some domains that require all agents to share the same context or involve many dependencies between agents are not a good fit for multi-agent systems today, and most coding tasks involve fewer truly parallelizable tasks than research.

What holds parallel work together

Before you start parallel workers, people or agents, write these down:

  • A plan with one entry per piece, fixing each piece's goal, interface and checks, plus a shared decisions section that binds everyone: the starting code, the pinned packages, and rules such as time-dependent code takes the current time from an injectable clock. This week's kit follows that rule.
  • Ownership and frozen shared pieces. Each worker edits only its own files. Shared files, such as a home page or a stylesheet, have one owner who integrates changes. Workers copy finished shared pieces; they never import another worker's unfinished files.
  • Dependencies ordered on purpose. A piece that reuses another piece's work starts after that work is finished.
  • Isolation beyond files. Each worker gets its own scratch folder and its own range of network ports.
  • An independent reviewer. When a piece is finished, someone who did not build it reviews it, and every finding is logged with a decision.

A plan cannot prevent every disagreement between pieces. It narrows where they can happen and says who fixes them.

Key idea

Plan the meeting points before you start the workers. Split by dependency, write the contract, give each worker its own worktree, test on the merged result, and keep a named person at the merge.

The long view of many hands

The lecture stayed with one merge. These four readings give the background: what Brooks actually argued, why git cannot see this kind of conflict, how teams keep main green, and whether Ana was right to store UTC at all.

R1

The Mythical Man-Month in context

Brooks wrote from experience. When in 1964 I became manager of Operating System/360, he recalls in the preface, he took over a project that at its peak had over 1000 people working on it. The book's second chapter asks why adding people so often fails to shorten a schedule, and it sorts tasks into four kinds by how time to finish changes as workers are added. His figures show the shapes; here they are as sketches.

For the last kind he is blunt: Since software construction is inherently a systems effort—an exercise in complex interrelationships—communication effort is great, and it quickly dominates the decrease in individual task time brought about by partitioning. Adding more men then lengthens, not shortens, the schedule. The chapter's worked example, which he calls the regenerative schedule disaster, adds two people to a late three-person task: they need training by the experienced people, the work must be repartitioned, and system testing grows.

Brooks came back to the law twenty years later, in the 1995 anniversary edition. He cites a 1991 book by Abdel-Hamid and Madnick, Software Project Dynamics, and quotes its conclusion: Adding more people to a late project always makes it more costly, but it does not always cause it to be completed later. Adding people early is safer than adding them late. His own verdict: I stand by the bald statement as the best zeroth-order approximation to the truth, a rule of thumb to warn managers against blindly making the instinctive fix to a late project.

What changes when the extra hands are agents? Some costs move. An agent needs no months of training, but it starts every session knowing only what it is given, and someone has to write that down. Some costs stay: the work still has to be partitioned, the pieces still have to fit, and every piece still has to be checked by someone accountable. Whether adding an agent to a late task makes it later is an empirical question about your work, not something Brooks or anyone else has settled for you. Week 11 is about measuring exactly that kind of effort.

R2

Semantic conflicts

Git merges text. When two branches change different lines, git combines them and reports success. It has no idea what the lines mean. Martin Fowler named the gap in 2011: By a semantic conflict I mean a situation where Jez and I make changes which can be safely merged on a textual level but cause the program to behave differently. In his longer 2020 guide to branching he adds that a developer must re-test after merging even if it's a clean merge, because even a clean merge can hide semantic conflicts.

How common is this? In a 2011 study, Brun, Holmes, Ernst and Notkin went through the version histories of nine open-source projects. In the three whose test suites they could run (Git, Perl5 and Voldemort), 16% of merges had a textual conflict, 1% merged cleanly but then failed to build, and 6% merged cleanly but then failed tests. Put differently, about a third of all the conflicts they found were invisible to the version control system. (These numbers are from the paper's results section; its one-line summary of them is easy to misread.)

You cannot make git understand meaning, but you can make a change in meaning loud:

  • Rename when the meaning changes. If Ana had renamed the field starts_at_utc, Ben's code, still asking for starts_at, would have failed on the merge with an error. A semantic conflict becomes one the tests see at once.
  • Use types that carry the meaning. A timezone-aware datetime instead of a bare string, or a small type such as UtcInstant, makes the wrong use harder to write.
  • Make readers strict. A reader that refuses a value it does not expect fails on the first merged run instead of printing a wrong hour for weeks.
  • Test both sides against one contract, as in class.
  • Integrate often. Fowler's advice in 2011 was simply to merge more often. Ana's and Ben's branches lived about a day. The longer branches live apart, the more meaning can drift between them.
R3

Merge queues

Many teams hold themselves to one rule: main always passes all the tests. That only works if each change is tested on top of the main it will actually land on. Here is what GitHub does, from its own documentation.

  • A pull request's checks test a merge, by default. A workflow triggered by a pull request checks out a merge branch unless it asks for something else, so Your CI tests run against the merged result, not just the head branch alone. But that result is computed with main as it was at that moment. When another pull request merges first, the green check is out of date.
  • "Require branches to be up to date before merging" closes the gap by force: in GitHub's words, it is there to ensure that pull requests are tested with the latest code on the protected branch. The price, also in GitHub's words: More builds may be required, as you'll need to bring the head branch up to date after other collaborators update the target branch.
  • A merge queue does the same work in order, without asking each author to update and wait. When a pull request joins the queue, its changes are grouped with the latest version of the base_branch as well as changes from pull requests ahead of it in the queue, tested in a temporary branch, and merged only if the required checks pass. One practical detail: GitHub Actions workflows run for a queue only if they are triggered by the merge_group event, so the CI file needs merge_group: next to pull_request:.

The last point is the one to remember. A merge queue, or the up-to-date rule, guarantees that the tests run on the merged result. It cannot invent the test that fails there. Put Ana's and Ben's branches through a queue with only their own tests, and the merged build goes through green, exactly as it did in class. The queue needs the integration test and the contract tests to have something to catch.

R4

Which time was right?

Ana chose to store UTC instants. For timestamps of things that have happened, like the moment a reservation was made, that is standard advice, and the AfterHours schema already stored created_at that way (…Z) while it stored starts_at as festival time. One schema, two conventions, and nothing in the column names to tell them apart.

For events that people schedule in a place, in the future, UTC is not the whole story. Jon Skeet argues that the common advice to convert everything to UTC is overly broad in my view. For future and near-past events, it doesn't take into account that time zone rules change, making the initial conversion potentially inaccurate. Time zone rules do change; in his words, This isn't a corner case, it's the normal way things work. An event at 20:00 on the local clock still happens when the wall clock shows 20:00, whatever the rules say by then. His preferred design keeps the local time and the zone's name, and treats UTC as derived data to be recomputed.

For a three-day festival two weeks away, Ana's choice is fine. For "every Friday at 20:00 next year", keeping the local time and the zone's name would be safer. Python's zoneinfo module reads named zones from the operating system, and where there is no zone database (Windows, notably), Python's documentation recommends declaring a dependency on the tzdata package. The lab kit avoids all of this with a fixed UTC+2 offset, which is exact only because every festival date falls in summer time.

So which time was right? Both representations are defensible. The bug was having two of them under one name, with nobody owning the choice. That is what the contract fixes.

Words from today

Worktree
An extra working folder attached to the same git repository, with its own checked-out branch and files. All worktrees share one history.
Merge base
The latest commit two branches have in common; where they started to differ (git merge-base).
Textual conflict
Two branches changed the same lines; git stops and asks a person.
Semantic conflict
Two changes that merge cleanly as text but make the program behave wrongly together.
Integration test
A test that crosses a boundary between parts built separately, such as typed time to shown time. In this lab the two parts disagree only once they are merged, so that is where the integration test catches the bug.
Integration contract
A short, owned document fixing what a shared thing means, with examples that tests on both sides use.
Contract test
A test of one side of a boundary against the contract's examples: the producer emits them, the consumer accepts them.
Critical path
The longest chain of tasks that must happen one after another. No number of workers finishes sooner.
Merge queue
A service that tests each change on top of the latest main and the changes ahead of it, and merges only if the tests pass.
Planner and workers
One planner splits the work and integrates; workers each do one part (also called orchestrator-workers).
UTC, offset
UTC is the reference clock. An offset such as +02:00 says how far a local clock is ahead of it.
Naive and aware
A Python datetime without a time zone is naive; one with a time zone is aware. replace(tzinfo=…) relabels; astimezone(…) converts.
Injectable clock
The one function the app asks for "now", so tests can fix the time.
