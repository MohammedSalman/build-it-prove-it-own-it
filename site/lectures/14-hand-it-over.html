0:00 – 0:15

The handover test

On Friday your team gives its AfterHours to another team and takes theirs. On Monday the festival organisers write to the new owners:

From the organisers

Some of our events don't need booking: the open jam in the courtyard, the chill-out room, the late-night food stalls. People just turn up. We'd like them in the programme as drop-in events. They must be clearly marked, nobody should be able to book one by mistake, and nothing about the events that do need booking may change. Each drop-in event still has a door limit, which we'd like to show.

The new owners must build it using only your repository. Until the challenge closes, you may not answer their questions, in person or in chat. This is the maintenance challenge, and it starts in this week's lab.

Predict, then list (1 minute alone, 4 minutes in pairs)
  1. Alone: how many minutes will the other team need, from git clone to a change they could safely release? Write a number.
  2. In pairs: list every question they will ask on the way. Next to each, write where in your repository the answer is. Leave it blank if the answer is only in someone's head.

Whatever the product, newcomers ask much the same questions, in much the same order. Here they are as a path, with the part of a repository that answers each one.

Stop 8 deserves a closer look. The Week 1 app creates its tables with CREATE TABLE IF NOT EXISTS. The obvious way to add a column is to edit schema.sql. We did exactly that on a copy, with the code that reads the new column, and started it against a database created by the previous version, the way the festival's laptop would:

$ python -m pytest -q               # every test makes a fresh database
8 passed in 0.12s
$ uvicorn app.main:app --port 9400  # on the festival's database, made last week
GET /api/events -> HTTP 500
sqlite3.OperationalError: no such column: e.kind

A real run, trimmed. The steps are in verification.md.

IF NOT EXISTS skips a table that already exists, so the edit reached every fresh database, including the one each test makes, and never reached the one in use. Nothing in the Week 1 repository says how its schema is supposed to change. The person who knew that would have had to be in the room. The kit's fallback repository answers it in its runbook and in a decision record: schema changes are numbered migration files that the app applies at startup, and a test checks that an existing database keeps its data.

What a fresh agent did (one run on each repository, 28 September 2026)

A coding agent starts every session knowing only what is in the repository and the prompt, so it is the most extreme newcomer there is. We gave the organisers' request and this week's acceptance examples to a fresh Codex session (gpt-6-astra) twice: once on the bare Week 1 repository, once on the kit's fallback repository with its handover documents. Its commands, answers and changes are saved in lectures/14-hand-it-over/demo/.

  • Both worked. Each run made drop-in events work in about four minutes, kept every existing test unchanged, and wrote tests for the examples. On a codebase this small, the documents did not decide whether the change worked.
  • The documents decided where the decisions went. On the fallback repository it read the README and AGENTS.md first, wrote the test before the code as the README asks, added a numbered migration, and recorded its decision next to the existing ones. On the bare repository it edited schema.sql, invented its own migration code, and started a new folder for decisions. Sensible choices, made in passing, that the next team would inherit as if someone had decided them.
  • Some questions no repository can answer. Both runs asked whether someone counts people at the door, and whether an existing event can become drop-in. Those belong to the organisers, on an open-questions list with an owner (Week 2).

One run each, with one agent: an observation, not a measurement.

Key idea

Quality includes whether someone else can own it. A repository someone else can own answers a newcomer's questions in the order they ask them, and it records the decisions so the next person follows them instead of making new ones by accident.

Key idea

Every document in a handover is a claim about the software, and the course rule applies to it: a claim needs evidence. Give each document a way to be checked: a command that runs, a test it names, the date it was true.

Knowledge that lives in one head

Some knowledge never reaches a document. One person set up the deploy, one person understands the retry logic, and everyone else is happy to leave it that way. The truck factor (also called the bus factor) names the risk: the smallest number of people who would have to leave before a project is in serious trouble. Avelino and colleagues estimated it from the commit history of 133 popular open-source projects on GitHub, and 65% came out at 1 or 2. When they asked developers what helps a project survive losing its key people, the most common answer was documentation, followed by an active community and automated tests. Their numbers are an algorithm's estimate for open-source projects, and they say nothing about student teams. The mechanism is the same everywhere, though, and you can draw it for your own team.

Your team's knowledge map (pairs from the same team, 5 minutes)
  1. List the five parts of your product most likely to change.
  2. For each, write who could change it tomorrow without help. Circle every part with one name.
  3. For each circled part: which document or test would let a stranger change it? Does it exist?

Keep the list. It is your handover to-do list, and it is your revision list for the defences.

Licences travel with the code

The new owners inherit your dependencies, and every dependency comes with a licence: the terms under which you may use, change and share it. Week 8 asked where a package comes from. The handover has to say what each one allows. The kit's scripts/licences.py follows requirements.txt down to the dependencies of dependencies and prints the licence each package declares. For the fallback repository that is 21 packages from 4 lines of requirements, all under permissive licences (MIT, BSD, Apache-2.0, PSF-2.0), which allow use, change and redistribution as long as you keep their copyright and licence notices. Declared metadata is a starting point, not proof: for anything unusual, read the licence file. Reading R2 goes on to code that an agent wrote.

Defend code you didn't type

The receiving team will own code they did not type. So do you, already: your product holds code your teammates wrote, code an agent wrote, and soon code the receiving team wrote. The course rule says every consequential decision needs an accountable human, and nobody can answer for code they cannot explain. The practical defences check exactly that. They are 25% of the course mark, and they run in their own slot after demo day.

MinutesPartWhat you may useWhat happens
1SamplenothingThe assessor draws two of the twelve question families at random; you choose one. They name a path in your team's product

Each part is scored 0 to 4; the kit proposes equal weights, and your instructor publishes the final scheme before the defences. Three rules from the rubric are worth knowing now:

  • Reasoning over luck. A wrong prediction with a clear mechanism scores higher than a right guess without one. If you find your mistake in the tools part and explain it, that counts too.
  • "I don't know, and here is how I would find out" is honest. Bluffing is not.
  • A second chance, and fair conditions. A student who cannot explain their part gets a targeted reassessment on that part. Approved adjustments (extra time, a written explanation, your own screen set-up) apply. How much you used an agent is never graded; whether you checked its work is.

The twelve question families are public, in defence/question-bank.md. That is deliberate. By the time you can defend every path in your product, you can own it.

How to explain code you did not type

  1. Start from the promise. What must stay true on this path? Say it in one line, the way Lecture 1 wrote confirmed ≤ capacity.
  2. Find the test that protects it. Its name and its expected values tell you what the authors thought mattered.
  3. Draw the request map. Files and functions in order, and the one place where the decision is made.
  4. If two things can happen at once, draw the timeline. The race timeline from Lecture 1 shows which orders are dangerous.
  5. Predict with tests. For any change, ask which tests would fail, which would still pass, and what a person using the app would notice.
Agent-off drill: a practice defence (pairs, 5 minutes, no laptop)

This is reserve() from the kit's fallback repository, simplified:

def reserve(event_id, attendee):
    event = SELECT id, capacity FROM events WHERE id = ?
    taken = SELECT COUNT(*) FROM reservations WHERE event_id = ?   # first check
    if taken >= event.capacity: raise SoldOut                      # → 409
    payments.authorize(attendee)                                   # about 300 ms
    BEGIN IMMEDIATE                                                # SQLite's write lock
    taken = SELECT COUNT(*) FROM reservations WHERE event_id = ?   # second check
    if taken >= event.capacity: ROLLBACK; raise SoldOut            # → 409
    INSERT INTO reservations (event_id, attendee); COMMIT          # → 201
  1. Explain (2 minutes). Maya and Sam press Reserve for the escape room's last place at almost the same moment, and Maya's request takes the lock first. Walk both requests through the code. Where does Sam find out he lost, and what has already happened to him by then?
  2. Predict (2 minutes, the other person). A teammate deletes the second check: "we already checked". Which tests fail, which still pass, and what does a person using the app see?
  3. One minute: the listener says what was missing from each answer.
Debrief: what a strong answer says

Explain. Both requests pass the first check (39 of 40 taken) and both authorise a payment, which is simulated and takes about 300 ms. Maya takes the write lock first, counts 39, inserts and commits: 201. Sam waits a millisecond or so for the lock, counts 40, and gets SoldOut: 409. By then Sam's payment has been authorised, and nothing releases it. The fallback repository lists that as known risk KR-3, which is exactly what its known-risks file is for.

Predict. Without the second check both insert, and the escape room has 41 reservations for 40 places. We deleted it in a copy of the fallback repository and ran the tests three times: every time, 1 failed, 14 passed. The one failure is the concurrency test, because its helper holds both people at the payment step until both have passed the first check. The sequential test "the last place goes to whoever asks first" still passes, because one request at a time never produces the dangerous order. A person sees what Maya and Sam saw in Lecture 1: two confirmations for one place.

A prediction that names the test and the reason it fails is a strong answer before anyone runs anything.

0:45 – 1:05

Who answers for it

In Week 3 we drew the chain of responsibility for one delegated change: a person starts it, the agent does the middle, and a person decides, on evidence, whether it goes in. A handover stretches that chain across two teams. During the challenge the receiving team answers for every claim in its pull request, and your team still decides whether to merge it, because the product is still yours. In a real handover the whole product changes hands, and the new owners can only take responsibility for what they can see. That is why the known risks belong in the package.

What professionals have written down

The ACM (the Association for Computing Machinery), a professional society for computing, publishes a Code of Ethics and Professional Conduct. The current version was adopted on 22 June 2018. It is addressed to "all computing professionals, including current and aspiring practitioners, instructors, students", and it calls itself "a basis for ethical decision-making". Four of its principles read like a handover checklist:

1.3 Be honest and trustworthy"provide full disclosure of all pertinent system capabilities, limitations, and potential problems to the appropriate parties"Your known risks, handed over before the new team finds them the hard way
1.6 Respect privacy"Only the minimum amount of personal information necessary should be collected in a system. The retention and disposal periods for that information should be clearly defined, enforced, and communicated to data subjects."Where attendees' names go, and when they are deleted (Fig 14.5)

The Code is a professional code, not a law, and most of it says should. It is useful because it names duties that no test will check for you.

Privacy by default

Some of this is law. In the EU and the EEA, Article 25 of the GDPR requires the organisation that decides how personal data is used (the controller) to make privacy the default:

GDPR, Article 25(2)

"The controller shall implement appropriate technical and organisational measures for ensuring that, by default, only personal data which are necessary for each specific purpose of the processing are processed. That obligation applies to the amount of personal data collected, the extent of their processing, the period of their storage and their accessibility."

A name is personal data: the regulation's definition names "an identifier such as a name". The UK has its own version, with the same wording in this paragraph, and other countries have other laws. None of this is legal advice; for your product, follow your university's data-protection rules. The engineering question is simpler and the same everywhere: where does a person's data go, and who chose that?

Accessibility by default works the same way. Week 9 made WCAG 2.2 at level AA the bar and gave you manual checks for it. In a handover, the default is that every new part meets that bar too. That is why the maintenance challenge has an accessibility example (D5): the drop-in marking must be text, and a keyboard user must meet no control that does nothing.

What your own numbers say

Lecture 1 drew a model (Fig 1.9): agents widened the "write code" part of the pipe, so the narrow part may have moved to checking. It said that whether this was true for your team was something to measure. Every lab from 1 to 13 ended by asking each of you, on your own and under a pseudonym, for three numbers: minutes spent producing (code, tests, text, prompts), minutes spent checking (running, reading, reviewing, comparing, measuring), and minutes spent integrating (merging, resolving conflicts, wiring parts together; 0 when there was none). Here is the method on a made-up class, so you can see what the chart shows before your own numbers appear.

Your instructor will now show the same chart made from your class's answers by the same script, analyse_minutes.py. It never shows a row about one student, and it hides any lab with fewer than five valid answers.

Before you believe the chart (open after you have seen the real one)
  • These are estimates from memory, written at the end of each lab. In the METR study from Lecture 1, developers believed AI had made them 20% faster and were measured as 19% slower. Feeling and measurement can disagree by a lot.
  • Every lab had a different task. A review lab (Lab 7) should show more checking than a lab where you built a feature. A difference between labs is mostly a difference between tasks, not a trend in how you work.
  • There is no comparison group. Nobody did the same lab without agents, so the chart cannot say what agents changed.
  • People stopped answering. If the students who stopped differ from those who kept going, the later labs describe a different group.
  • It cannot say whether the checking was worth it: how many problems it caught, or what it missed.

What it can do is replace impressions with numbers you can question, and give you a baseline for the next time you measure your own work. Say what it shows, and say what it cannot.

After the handover

The lecture handed AfterHours over. These three readings follow what comes after: what happens to its documents, who owns the code nobody on the team typed, and which skills you take with you.

R1

Documents that decay

Documents drift away from the code they describe. In a 1994 essay on software aging, David Parnas described what happens when people who never understood a design keep changing it: After many such changes, the original designers no longer understand the product. Those who made the changes, never did. In other words, nobody understands the modified product. He added a sentence every maintainer recognises: The documentation becomes increasingly inaccurate thereby making future changes even more difficult.

Studies of working engineers agree, with a twist. In 2003 Lethbridge, Singer and Forward confirmed that engineers do not update documentation as promptly or as completely as their managers want, and also found that out-of-date documentation remains useful in many circumstances. So the realistic aim is documents whose staleness you can see, and some kinds of document manage that much better than others.

  • Make it run. Python's doctest searches for pieces of text that look like interactive Python sessions, and then executes those sessions to verify that they work exactly as shown. The same idea works beyond Python: CI can run the README's commands; scripts/licences.py regenerates the licence table from what is installed; the fallback repository's tests/test_runbook.py runs the runbook's backup and check commands on every test run.
  • Date it and never edit it. Michael Nygard's decision records are kept after they are reversed, marked superseded, because it is still worth knowing what the decision was. A dated record cannot go stale about its own date.
  • Otherwise, keep it short, or delete it. Every sentence nobody checks is one more sentence that will one day be wrong.

The fallback repository's README says 15 passed. The moment the maintenance challenge adds tests, that line is wrong. The reference solution fixes it in the same pull request, which is exactly what example D6 asks for.

R2

Who owns generated code?

Your repository now holds code from many hands: yours, your teammates', an agent's, a package's, perhaps a snippet from a web page. Handing it over raises three separate questions, and the law answers them differently in different countries. This reading describes what we could check in September 2026. It is not legal advice, and your university and any future employer have their own rules about who owns what you write.

1. Can anyone own what an agent wrote?

In the United States, the Copyright Office concluded in January 2025 that Copyright does not extend to purely AI-generated material, or material where there is insufficient human control over the expressive elements, and that, with today's tools, prompts do not alone provide sufficient control. What a person adds is protectable: their own expression that shows in the output, and their creative selection, coordination, or arrangement or creative modifications of it. In March 2025 a federal appeals court held, in Thaler v. Perlmutter, that the Copyright Act requires a human author, while noting that this does not prohibit copyrighting work that was made by or with the assistance of artificial intelligence. The Supreme Court declined to hear the case in March 2026. That case was about a picture, not code.

The United Kingdom is unusual. Since 1988 its copyright law has protected "computer-generated" works that have no human author, treating as the author the person by whom the arrangements necessary for the creation of the work are undertaken. In March 2026 the UK government proposed removing that protection; as of September 2026 the law has not changed. Two countries, two answers, and both still moving.

2. What came with it?

Code arrives with obligations. Every dependency carries a licence. Python packages can now declare it as a standard SPDX identifier such as MIT, in a metadata field that PEP 639 introduced, which is what the kit's licences.py reads first. A snippet copied from a web page carries the page's terms: write down where it came from, next to the code. And code an agent suggests can occasionally match public code. GitHub's Copilot, for example, can block such suggestions, or show where matching public code came from and its licence; GitHub says matches typically happen in less than one percent of suggestions, and it only searches public code on GitHub.

3. Who answers for it?

Whoever ships it. Even where nobody can own generated code, somebody answers for what it does. That is why the course asks you to disclose meaningful help from agents and to own every claim you submit, and why the handover checklist asks you to record where copied material came from (item F3), without asking for chat logs.

R3

Skills that compound

Nobody knows what software jobs will look like when you graduate, and anyone who tells you with certainty is making a prediction. What this course can show you is which skills it needed every week, whichever tool wrote the code:

  • Saying precisely what must stay true (Weeks 1, 2, 6).
  • Getting expected answers from somewhere other than the code (Week 5).
  • Reading code you did not write, in order of risk (Weeks 7, 14).
  • Putting each decision that will change behind a boundary (Week 4).
  • Making the dangerous case happen on purpose (Weeks 1, 6, 10).
  • Measuring instead of trusting a feeling (Weeks 1, 11).
  • Running software for real, and getting back from failure (Weeks 12, 13).

None of these belongs to one tool, so each new tool makes them more useful instead of replacing them. That is what compounding means here. DORA's 2025 report says something similar about teams: AI's primary role is as an amplifier, magnifying an organization's existing strengths and weaknesses.

Learning with agents, without hollowing out

The worry is simple: if the agent does the work while you learn, do you learn? A few careful studies give a first, partial answer.

  • Bastani and colleagues (PNAS, 2025) ran a randomised field experiment with nearly 1,000 high-school students in Turkey practising maths (Fig 14.11). Students also do not perceive any reduction in their learning when they copy solutions. It is one school, one subject and one term, with a 2023 model.
  • Shen and Tamkin (Anthropic, January 2026) randomly assigned 52 mostly junior developers to learn Trio, a Python library new to them, with or without an AI chat assistant (OpenAI's GPT-4o). On a quiz straight afterwards the AI group averaged about 50% and the others about 67%, and the AI group was not significantly faster. The biggest gap was on debugging questions. Those who used the assistant to ask for explanations did much better than those who handed it the code, though those groups were small. It is a preprint from a company that sells AI tools, with one task of about an hour.
  • Lee and colleagues (CHI 2025) surveyed 319 knowledge workers: those who reported more confidence in generative AI also reported less critical thinking. That is an association in self-reports, not a cause.

None of these is about you, and none settles the question. Together they suggest that the same tool can do your thinking for you or support it, and that which one happens depends on how you use it. The habits this course built in are the ones that keep it supporting: predict before you run; do the agent-off drills; when you are learning, ask for hints and explanations instead of answers; debug by hand sometimes, because that is where the gap was largest; explain code before you accept it; and measure your own work instead of trusting how fast it feels.

Handover package
The documents and checks that let someone else own the software: a README that runs, AGENTS.md, decision records, a runbook, known risks, licences, and the evidence behind the product checklist.
Onboarding path
The questions a newcomer asks, in order, from getting the code to changing it safely (Fig 14.1).
Maintenance challenge
This week's handover test: another team adds drop-in events to your product using only your repository.
Fallback repository
The kit's handover-ready AfterHours, for a receiving team that cannot run its partner's product.
Known risk
Something already wrong or unsafe, written down with who it hurts, how you know, what limits it today and what would fix it.
Truck factor (bus factor)
The smallest number of people whose leaving would put a project in serious trouble.
Migration
A numbered, recorded change to a database schema that also reaches databases already in use. An expand-only migration only adds (a table, a column with a default), so the previous version can still run on the new schema without losing data. Whether it still behaves correctly depends on what the new rows mean: after drop-in events exist, the old version would book them.
Practical defence
Explain a sampled code path unaided, predict a change's effect, then diagnose or modify it with tools.
Personal data
Information about a person who can be identified. A name is enough.
Privacy by default
Collecting, keeping and showing only the personal data each purpose needs, unless someone deliberately chooses more.
Provenance
Where a piece of code came from, and what obligations came with it.
Permissive licence
A licence that allows use, change and redistribution as long as its notices are kept, such as MIT, BSD or Apache-2.0. Its SPDX identifier is the short standard name, such as MIT.
Evidence portfolio
Four of your decisions, each traced requirement → decision → change → check → result.
