Week 13 · Keeping old promises in new code

Change Without Forgetting

Most of a system's life comes after its first release, and most of its changes are made by people who did not write it: new teammates, future you, and now agents. This lecture is about changing a running system, its code and its data, without breaking a promise it has already made.

90-minute lecture 2-hour lab ~25 minutes of reading after class Homework: finish your own migration (~2 h) Kit: AfterHours v1 and v2 on one database Loop: Observe → Understand

By the end of today you can

0:00 – 0:15

Eight servers, one stale

On 1 August 2012 the New York Stock Exchange was due to start a new programme for retail orders, and the broker Knight Capital had written new code to take part. The code went into Knight's order router, a system called SMARS that ran on eight servers. This is what the US Securities and Exchange Commission (SEC) later found.

Case: Knight Capital, 1 August 2012

In about 45 minutes, Knight's router sent millions of orders (4M+ executions in 154 stocks, 397M+ shares) and Knight lost over $460 million. New code repurposed a flag that once activated old "Power Peg" code still on the servers; a technician did not copy the new code to one of eight servers, with no second review.

Take it apart one step at a time. Every detail below is from the SEC's order.

  1. Old code stayed. Power Peg was a feature Knight stopped using in 2003. Its code was never deleted: the SEC calls it "present and callable".
  2. The old code was changed and not retested. In 2005 Knight moved the part of Power Peg that kept count of the shares already filled. Knight did not retest Power Peg afterwards.
  3. A flag got a new meaning. The new code reused the flag that used to switch Power Peg on. The plan was to delete Power Peg, so that the flag would now switch on the new code instead.
  4. One server was missed. The new code was copied to the servers in stages from 27 July. One of the eight never got it, and nobody checked.

On the morning of 1 August, orders arrived with the flag set. Seven servers ran the new code. The eighth ran Power Peg, which, with its counting moved away, kept sending orders without noticing they had been filled.

Read the case carefully

Legally, the SEC's order is about risk controls. The SEC found that Knight had violated the Market Access Rule (Rule 15c3-5), which requires brokers to appropriately control the risks associated with market access, and Knight settled without admitting or denying the findings. The order lists missing controls from deployment to monitoring, so read it as the failure of a whole system of safeguards. One technician's missed copy is only the first link.

In pairs (3 minutes)

Knight's failure needed three ingredients: old code that could still run, a flag whose meaning changed, and a deploy that reached seven servers out of eight. For each one, name a check that would have caught it before 1 August.

What Knight's own systems showed that morning (open after the pairs)

From about 8:01 a.m., before the 9:30 market open, an internal system sent 97 automated emails that mentioned SMARS and an error called "Power Peg disabled". They were not designed as alerts, and staff did not usually read them. The evidence was there; nothing turned it into a stop.

During the incident, trying to fix the problem, Knight removed the new code from the seven servers where it had been installed correctly. That made things worse: now those servers also ran Power Peg when the flag arrived. Rolling back is only safe if the old version is still safe to run.

The SEC's order also says what one check could have done: "a written procedure requiring a simple double-check of the deployment of the RLP code could have identified that a server had been missed and averted the events of August 1."

Your three checks probably look like these: delete code you no longer use (it can't run if it isn't there); never give an old flag name a new meaning; after a deploy, ask every server which version it runs, and compare.

AfterHours has all three ingredients this week. The festival wants multi-day passes, which changes how tickets are stored. The gate servers are replaced one at a time while the gates are open, so for a while the old version and the new one run side by side on one database. And there is a flag in the database that nobody has touched since the 2025 festival.

Key idea

Maintenance keeps promises while it replaces the implementation. The code, the data layout and the flags all change. What each user was promised must not.

0:15 – 0:30

Photograph before you change

Before you change code you didn't write, find out what it does today. On the engineering loop from Lecture 1, this week starts at Observe: watch what the running code actually does, and feed that back into Understand before anyone specifies or delegates the change.

Michael Feathers's book Working Effectively with Legacy Code (2004) is about exactly this problem. His definition of it is short: To me, legacy code is simply code without tests. One of his main tools is the characterization test: a test that records what the code does now, so that you notice when a change changes it. On his blog he put the purpose this way: The purpose of characterization testing is to document your system's actual behavior, not check for the behavior you wish your system had.

The method is almost mechanical. Put the code in a test, write an expected value you know is wrong, run it, read the real answer in the failure, and paste it in as the expected value. In the same post Feathers describes it as supplying a dummy expectation value, and then running the test to find the actual one. Repeat for every situation you care about.

Here is the code that moves a ticket to another day in AfterHours v1, the version that runs today. Maya holds a Friday ticket and Sam a Saturday ticket. The festival runs Friday 9 to Sunday 11 October.

def change_day(ticket_id, new_day, now):
    row = ...SELECT id, holder, day, code FROM tickets WHERE id = ?...
    # A ticket can move until the day begins.
    if now >= _starts(new_day):            # 00:00 at the start of new_day
        raise ChangeRefused(...)            # → HTTP 409
    ...UPDATE tickets SET day = ? WHERE id = ?...   # → HTTP 200

Simplified from v1/tickets.py in the lab kit.

The code checks only the new day. So Maya can scan in on Friday evening, move her ticket to Saturday, and come back the next day. We planted this defect in the kit on purpose, and it is labelled as planted in the instructor notes. It is also a very ordinary bug: the comment "until the day begins" never says which day.

This is Week 5's warning from the other side. A characterization test takes its expected values from the code, so it can never show that the code is wrong. That is fine. Its job is to tell you, during a change, that behaviour moved. Feathers again: When a system goes into production, in a way, it becomes its own specification. People rely on what it does, bugs included.

So what do you do with a photographed bug in the middle of a migration? Keep the photograph, label it, and tell the product lead. Fix it later, in its own change, with a new test written from T3. During the migration both versions of the app must give Maya the same answer. If v2 quietly fixed the bug and v1 didn't, her answer would depend on which server took her request.

Key idea

Photograph first, judge second. A characterization test tells you when behaviour changed. The requirement tells you whether it was right. Keep the two apart, and never fix a bug inside a migration.

0:30 – 0:50

Expand, migrate, contract

The organisers' new requirement (T5): a festival pass covers two or three consecutive days and admits its holder on each of them. v1 stores one day per ticket, in the column tickets.day. A pass needs a range. The obvious change is one migration:

ALTER TABLE tickets RENAME COLUMN day TO first_day;
ALTER TABLE tickets ADD COLUMN last_day TEXT;

Now think about Friday night. The gates are open, so the servers are updated one at a time: this is a rolling deploy. For a while some gates run v1 and some run v2, and all of them use one database. The moment the rename runs, every v1 server asks for a column that no longer exists. That is Knight's eighth server again: old code, still running, meeting a change it was never told about.

The fix is an old refactoring pattern. Danilo Sato described it on Martin Fowler's site in 2014: Parallel change, also known as expand and contract, is a pattern to implement backward-incompatible changes to an interface in a safe manner, by breaking the change into three distinct phases: expand, migrate, and contract. A database table is an interface too, shared by every version that runs against it. Sato adds that most database refactorings follow the same pattern, with the migrate phase as the transition period between the old and the new schema.

PhaseWhat changesTickets table afterwardsWho can run on it

MigrateCopy day into the new columns for every existing ticket (the backfill), while both versions keep writingsame columns, new ones filledv1 and v2
ContractOnce v1 is gone, drop day and make the new columns requiredfirst_day, last_dayv2

Debrief: the order, and what each swap breaks

The kit's order is C, B, F, E, G, D, A, H: expand, deploy v2, backfill, retire v1, backfill again and verify, passes on sale, contract, compare meaning. Some swaps are harmless; the table shows which are not.

If you swap……this breaks
B before Cv2 starts on a table with no first_day. In the kit, v2 refuses to start.
E before FNothing breaks: v2's read rule covers rows the backfill hasn't reached, and with v1 gone there are no late writes to catch up with. You give up the option of falling back to v1 while v2 proves itself.
A before EEvery v1 server still running asks for day and fails. The kit's contract step refuses: v1 is still live.
A before GTickets v1 sold or moved after the first backfill lose what v1 wrote. The kit's contract step refuses: rows are missing or disagree.
D before EA v1 gate reads only day, which holds a pass's first day. It admits the pass holder on Friday and turns them away on Saturday. The kit refuses to switch passes on until v1 is recorded as retired.
H skippedYou have no evidence that anything survived. Every step can report success while tickets quietly change meaning.

Two of the steps can't be undone by redeploying v1. Until passes go on sale you could go back to v1 alone: v1 ignores the new columns. After passes are sold, v1 would turn their holders away. After the contract, the old column is gone, so v1 can't run at all. Going back from there needs work you have prepared and tested: a reverse migration that rebuilds day (possible while no passes exist), a repair forward, or a restore (Week 12) that also deals with every write made since the backup. The kit supplies none of these, which is why these steps come last and have guards.

The kit supplies v2 with a compatibility strategy: two rules for the window, written at the top of v2/tickets.py.

  • Write rule. While day exists, v2 keeps it in step: every ticket v2 writes has day, first_day and last_day. (For a pass, day holds its first day.)
  • Read rule. While day exists, it is the truth for day tickets. v1 writes only day: its new tickets have no first_day yet, and it may move a ticket after the backfill has copied it.

That second sentence hides the hardest case of the week. Follow one row.

So the backfill in the kit has rules, and part A3 of the lab is writing it: fill every day ticket's new columns from day; never touch a pass; be safe to run again; catch up with tickets v1 sold or moved after an earlier run; and change at most a batch of rows per transaction, because SQLite has one write lock for the whole database (Lecture 1) and the gates are selling while you copy.

The contract step then refuses unless four things hold, and it checks them inside the transaction that rebuilds the table, after taking the write lock. Checking first and rebuilding later would be check-then-act, the Lecture 1 race, with a v1 write landing in the gap.

-- the contract step refuses unless all of these are 0 (and v1 is recorded as retired)
SELECT COUNT(*) FROM tickets WHERE first_day IS NULL OR last_day IS NULL;       -- missing
SELECT COUNT(*) FROM tickets WHERE first_day = last_day AND first_day <> day;  -- disagree
SELECT COUNT(*) FROM tickets WHERE first_day > last_day;                        -- backwards

How do you know it worked? The kit's rehearsal copies "production" (600 tickets), then runs the whole migration while v1 and v2 sell and move tickets through the real apps, and records every write the apps confirmed. At the end it compares what each ticket means (who it admits, on which days) with that record. One real run, shortened:

Key idea

Change the shape of shared data in steps that each keep every running version working. The steps you can't undo by redeploying the old version come last, and they check before they act. Prove the result by comparing what the data means, with writes still arriving.

0:50 – 1:05

Flags, dead code, and Hyrum's law

A feature flag is a switch, read by running code, that turns a code path on or off without a deploy. The kit uses one to put passes on sale: multi_day_passes, stored in the database so that every server sees the same value. Pete Hodgson's article on feature toggles (martinfowler.com, 2016) sorts them by purpose: release toggles, experiment toggles, ops toggles and permissioning toggles. Release toggles, like ours, are meant to be temporary; ops and permissioning toggles can be long-lived on purpose, such as a kill switch. He is blunt about the cost of keeping toggles around: Savvy teams view the Feature Toggles in their codebase as inventory which comes with a carrying cost and seek to keep that inventory as low as possible. Some teams put expiry dates on their toggles, and some add "time bombs" which will fail a test (or even refuse to start an application!) once a toggle outlives its date.

AfterHours has a flag stuck halfway. In the flags table there is a row called wristband_mode, off since 11 October 2025. Its note says that on the first night of the 2025 festival the scanners failed, so volunteers checked paper wristbands by eye and let every ticket in. The code is still there, in v1 and in v2, because v2 was copied from v1:

if flags.enabled(conn, "wristband_mode"):
    # Festival 2025: the scanners failed on the first night, so volunteers checked
    # paper wristbands by eye and every ticket was let in.
    return {"admitted": True, ...}

That is dead code in the Knight sense: it never runs under today's settings, and it is still present and callable. Dead code costs you twice. People and agents have to read it and wonder whether it matters, and one wrong setting brings it back to life.

Predict (pairs, 3 minutes)

A pull request, written in the style an agent might produce, says: "Reuse the unused wristband_mode flag to put passes on sale, instead of adding a new flag." It changes one line in v2's buy_pass. The release steward merges it on Saturday afternoon, during the migration window, and switches the flag on. At 18:00 Maya scans her Friday ticket at a gate that still runs v1. What happens? What happens at a v2 gate?

We authored this pull request for the lecture. It is not output from a real agent.

Answer

Both gates let her in. v1's scan() still reads wristband_mode as "let every ticket in", and so does v2's, because the pull request changed only buy_pass. Every ticket is now valid every day, at every gate. Passes are also on sale while v1 gates still run, which T6 forbids, and the kit's guard never fired: it protects the name multi_day_passes, and this switch has another name. The kit has a test that photographs exactly this for v1: with the flag on, a Friday ticket is admitted on Saturday (HTTP 200).

That is Knight in miniature: an old name given a new meaning, read by old code that was never removed. The rules that prevent it are short. A new behaviour gets a new flag. Delete a flag's readers before its row, and delete dead code once it is switched off for good; version control remembers it for you. Part A5 of the lab removes the reader from v2. v1's copy goes when v1 retires, and only then can the row go.

A flag is behaviour someone chose to make switchable. Much more behaviour is visible without anyone choosing it. Hyrum Wright made an observation about it while improving Google's core C++ libraries, where even a small library change could break some far-off system; Titus Winters named it Hyrum's law:

With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody.

AfterHours shows it at small scale. Requirement T4 promises only that ticket codes are unique. What anyone can observe is more: codes look like FRI-0001, and they keep their prefix when the ticket moves, so Maya's Saturday ticket still says FRI. If a door volunteer's tablet colours the screen by those three letters, that format has become a promise nobody wrote down. The characterization tests in the kit photograph it and label it observed, not promised, and v2 keeps it for day tickets. Reading R2 goes further.

Key idea

A release flag is a temporary branch in running code. Give every flag an owner, give a temporary one an end date, remove its readers before its value, and never give an old name a new meaning. Anything users can observe, somebody depends on: decide on purpose which of it you promise.

The third job is the large mechanical change: rename day everywhere, add a column to every query. We did not measure an agent on this one. The risk is easy to see anyway: the edit is mechanical, the order is not. Which reads must stay on day during the window is the read rule, a decision written in the migration plan and at the top of v2/tickets.py; a rename applied everywhere at once breaks it. Give the agent the plan as context, ask for one step per change so that each diff can be reviewed and deployed alone, check that the edit reached every place it should (search for what is left, run every suite), and let the checks decide: the characterization tests on both versions, the step's own tests, and the rehearsal.

After class · about 25 minutes

Software that keeps its word

The lecture changed one table. These four short readings are about why systems keep needing changes like it, and how to make them without surprises. Read them before the lab.

R1

Software that is used must change

In 1980 M. M. Lehman published five laws of program evolution, formulated, in his words, following quantitative studies of the evolution of a number of different systems. He first sorted programs into kinds. S-programs are programs whose function is formally defined by and derivable from a specification. At the other end are E-programs, which mechanize a human or societal activity. A festival booking system is an E-program: the festival changes, so the program must.

His first two laws, in the 1980 wording:

  • Continuing change. A program that is used and that as an implementation of its specification reflects some other reality, undergoes continual change or becomes progressively less useful.
  • Increasing complexity. As an evolving program is continually changed, its complexity, reflecting deteriorating structure, increases unless work is done to maintain or reduce it.

This week is a small case of both laws. Passes are continuing change. The migration adds complexity: v2 carries a write rule, a read rule and a new flag. The "unless work is done" part is the contract step, the removal of wristband_mode, and, after passes are permanent, removing the window code from v2. A migration that never contracts leaves the system more complex than before it started; Sato's article says the same about parallel change.

Read the laws as observations about the systems Lehman studied, which he kept revising: a 1997 paper with his colleagues lists eight, and restates the first as E-type systems must be continually adapted else they become progressively less satisfactory.

R2

Every behaviour has a user

Hyrum's law comes from maintaining widely used code at Google: With a sufficient number of users of an API, it does not matter what you promise in the contract: all observable behaviors of your system will be depended on by somebody. The book Software Engineering at Google (2020) gives the classic example. The order in which a hash table returns its keys is not promised, yet programs come to depend on it, some even using it as a cheap source of randomness, so changing that order breaks them. Wright's own page names the result: bug-for-bug compatibility. That is exactly what the lab's characterization tests ask of v2 during the window.

You can't stop people depending on behaviour, so manage it. Decide which observable behaviours are promises, write them into the requirements, and test them. Change the rest deliberately: say so in advance, and give users time (R3). Photograph at the level of the promise: the kit's characterization tests compare only the fields v1 returned, and they label the code format as observed and unpromised. When a photograph fails, the question is always the same: did a promise change, or only something nobody promised?

R3

Deprecation is a process

In the lab, retiring v1 ended with one command, retire v1, and that command only records a decision. Someone has to stop every v1 server and check first. The guards trust the record; they cannot see which servers are still running. In a real system, retiring an old version, an old API field or an old table takes months, and it rarely happens by itself. The chapter on deprecation in Software Engineering at Google, by Hyrum Wright, defines it as the process of orderly migration away from and eventual removal of obsolete systems, and starts from the premise that code is a liability, not an asset.

It separates two kinds. Advisory deprecations don't have a deadline and aren't high priority for the organization; they announce and hope. As our friends in SRE will readily tell you: "Hope is not a strategy." Compulsory deprecations come with a deadline, an enforcement mechanism, and a team that owns the migration: without explicit owners, a deprecation process is unlikely to make meaningful progress, no matter how many warnings and alerts a system might generate.

AfterHours has a deprecation waiting. v2 still returns the field day in every ticket response, because any client written against v1 may read it. The database column is gone after the contract step, and the API field isn't. Removing it is its own expand, migrate, contract, on a slower clock, because you don't control the clients. Before removing it, measure: which clients still read day, and who owns moving them?

R4

Compare meaning, not bytes

After a migration it is tempting to prove nothing was lost with a checksum: hash every row before, hash every row after, compare. Across a schema change that can't work. The rows have different columns, so the bytes differ even when nothing was lost. And a checksum of only the columns both shapes share (id, holder, code) would pass even if every ticket had lost its day.

So define meaning in terms of what the application does with the data. For a ticket, that is who it admits and on which days. The kit's migrations/meaning.py reads that from any shape of the table, using the same read rule as v2, and migrate.py meaning --compare reports every ticket whose meaning changed.

Two cautions. First, "the same as before" is the wrong expectation for a live migration: tickets are sold and moved during it. The rehearsal handles that by keeping its own record of every write the apps confirmed and comparing against the record. Second, a meaning check is only as good as its definition. Ours includes the holder, the code and the days. It would not notice a lost created_at, so the contract step's tests check separately that every kept column is copied unchanged. Write down what your data means before you move it, and check that, with writes still arriving.

W

Words from today

Legacy code
In Feathers's definition, code without tests: you can't change it and know whether you changed its behaviour.
Characterization test
A test that records what the code does now, right or wrong, so that a change shows up as a failure. Its expected values come from the code.
Rolling deploy
Replacing servers one at a time while the service keeps running, so old and new versions run side by side for a while.
Parallel change (expand, migrate, contract)
Making an incompatible change in three phases: add the new form next to the old, move everything to it, then remove the old.
Migration window
The time during which more than one version runs against the same data. In the lab: between deploying v2 and retiring v1.
Backfill
Filling new columns for rows that already exist. It must be safe to run again and able to catch up with late writes.
Guard
A check a step runs before it acts, refusing if its preconditions don't hold. The contract step's guard runs inside its own write transaction.
Feature flag
A switch read by running code that turns a path on or off without a deploy. Every flag needs an owner; a temporary one, such as a release flag, also needs an end date.
Dead code
Code that never runs under current settings but is still present and callable.
Hyrum's law
With enough users, every observable behaviour of a system is depended on by somebody, whatever the contract promises.
Deprecation
The managed process of moving users off an old system and then removing it. Advisory: no deadline. Compulsory: a deadline, enforcement and an owner.
Meaning check
Comparing what data means to the application (here: who is admitted on which days) instead of comparing bytes, so that data can be compared across schemas.
