Boundaries That Make Change Cheap

An agent can add a feature to any codebase. What the next change costs depends on where the decisions live: in one place, or copied into routes, SQL, web pages and notes. This lecture is about drawing boundaries around the decisions most likely to change.

90-minute lecture 2-hour lab ~25 minutes of reading after class Kit: tangled AfterHours Loop: Specify (design)

By the end of today you can

  • Find every place a decision is written down, and say what a change to it will touch.
  • Split a system by the decisions likely to change, instead of by the steps of the flow.
  • Tell a deep module from a shallow one, and sketch a small interface for a rule.
  • State the units and meaning of what crosses a boundary, and use types to guard them.
  • Keep a refactor (the existing tests untouched and green) apart from a behaviour change (tests change on purpose).
  • Record a design decision as an ADR, including an alternative you rejected.

0:00 – 0:12

One rule, two codebases

AfterHours has grown since Week 1. One prompt at a time, features were added: people can cancel a booking, see My bookings, and volunteers can check people in at the door. Every feature works, and all 33 tests pass.

Then the organisers send a one-line email:

From the organisers, 1 October

From next week, cancellations are allowed until 24 hours before the event. After that, people keep their place.

Today the rule is "cancel any time before the event starts". The change sounds like one line. Whether it is one line depends on how many places in the code know the rule.

Predict, then hunt (pairs, 6 minutes)
  1. Before you look: how many places in the code will this change touch? Pick one: 1, 2–3, 4–6, 7 or more.
  2. Now open the kit (lectures/04-boundaries/lab-kit/tangled/, projected at the front). Find every place that states, checks or shows today's rule. Count places that are not Python too.

Here is one place that is easy to miss. It is the query behind My bookings, in app/main.py:

SELECT r.id, r.event_id, e.title, e.venue, e.starts_at, r.status,
       e.starts_at AS cancel_until,                          -- the rule, as a column alias
       CASE WHEN r.status = 'confirmed' AND e.starts_at > ?  -- the rule again, as text comparison
            THEN 1 ELSE 0 END AS can_cancel
FROM reservations r JOIN events e ON e.id = r.event_id
WHERE r.attendee = ?

The deadline hides in a column name. The check hides in a comparison of two strings.

Seven places, plus a comment that restates the rule, in three files and four languages. We made the change there by hand, correctly: 8 separate edits in 3 files, and the five new-rule API tests (tests/new_rule/test_cancel_24h.py) pass. In a modular version of the same app, with the same behaviour and the same 33 tests of that behaviour, the change was 2 lines in 1 file. Both diffs are in lectures/04-boundaries/demo/.

One trap on the way. To move the deadline back 24 hours in SQL, SQLite's datetime(e.starts_at, '-24 hours') looks right. It returns 2026-10-08 20:00:00, with a space where our stored times have a T. Compared as text with 2026-10-08T19:00:00, it says "not later", so on the deadline's own day the Cancel button disappears too early. The tests would catch it only if one of them happened to use a time on that day.

About this code

We built the tangled kit on purpose, the way an app tends to look after features are bolted on one prompt at a time. It is a teaching construction, not the output of one particular agent. It works, and every characterization test passes. One oddity on the door page is planted and pinned by a test; the lab explains it.

Key idea

What a change costs is decided before anyone makes it: by how many places know the thing that is changing.

0:12 – 0:30

Hide what will change

How did the rule end up in seven places? Each feature was built as a flow: a request comes in, rows are read, something is checked, rows are written, a response goes out. Cancelling is one flow, My bookings another, booking a third. Each flow needed to know the rule, so each got its own copy.

In 1972 David Parnas compared two ways of splitting the same small program into modules. The program built a KWIC index: it took lines of text, produced every circular shift of every line, and printed them in alphabetical order. His first split followed the processing steps, one module each for input, circular shift, alphabetizing and output. His second gave each module one design decision to keep to itself; one module, for example, alone knew how the lines were stored in memory.

Then he asked what would happen to each split when a likely decision changed. Changing how lines are stored, or packing four characters into each machine word, touched every module in the first split, because they all used the storage format directly. In the second split, only the storage module changed. His conclusion:

We have tried to demonstrate by these examples that it is almost always incorrect to begin the decomposition of a system into modules on the basis of a flowchart. We propose instead that one begins with a list of difficult design decisions or design decisions which are likely to change. Each module is then designed to hide such a decision from the others.

D. L. Parnas, Communications of the ACM, December 1972

He called the criterion information hiding. A module is a boundary around a secret: everyone else knows only what they can ask it, never how it decides.

Decision cards (pairs, 8 minutes)

Here are eight decisions inside AfterHours. For each, say how likely it is to change this year, and who would change it. Then group them into modules so that each likely change lands in one module.

  1. How long before the start people may cancel.
  2. When the door opens and closes for check-in.
  3. What counts as a taken place (confirmed bookings only? places kept back for volunteers?).
  4. Which database we use (SQLite today).
  5. How a payment is authorised (the provider).
  6. How the door page looks.
  7. The text format of times stored in the database.
  8. How people identify themselves (a typed name today; logins in Week 8).
Debrief: one reasonable grouping
  • Time rules (1, 2): the organisers change them, often together. One module, policy.
  • What counts as taken (3): product decisions, and they will change; Week 6's optional waitlist design explores how the count might change. One module, catalog, owns the count.
  • Storage (4, 7): engineering decisions that change rarely but hurt everywhere when they do. Keep SQL and stored formats behind the modules that own the tables, and convert text to datetime at that edge.
  • Payments (5): already its own module in Week 1, so a new provider changes payments.py, not the routes.
  • The door page (6): the most likely change of all, so keep rules out of the page. The page shows what the API says.
  • Identity (8): not hidden anywhere yet; today's typed name leaks into every route. Week 8 will pay for that.

Other groupings can be right. Test yours the way Parnas did: pick a likely change and count the modules it touches.

Key idea

Split a system by the decisions you expect to change, not by the steps a request goes through. Each module keeps one secret.

0:30 – 0:45

Deep modules

A boundary helps only if the secret stays inside it. John Ousterhout's book A Philosophy of Software Design (2018) gives a way to see whether it does. Picture a module as a rectangle. The top edge is its interface: everything a caller must know to use it. The area is the work it does for them. In his words: The best modules are those that provide powerful functionality yet have simple interfaces. I use the term deep to describe such modules.

One of his examples is file input and output in Unix, which he calls a beautiful example of a deep interface: five basic system calls (open, read, write, lseek, close) in front of everything the operating system does to store files. He also names the symptom that tangled code shows: change amplification, when a seemingly simple change requires code modifications in many different places. That is our hook.

Here are two ways to take the cancellation rule out of the routes.

Quick check (pairs, 3 minutes)

The organisers change 24 hours to 48. With the shallow helper, which files change? With the deep module? And which version do you trust an agent to change without missing a caller?

Answer

Shallow: every caller that passes -24 or writes the message, so three places at least, plus the page and the docs if they state the rule. Deep: one constant and one sentence in policy.py. The helper module made the code shorter without hiding the decision.

Deep does not mean big, and more modules is not better. Ousterhout calls the opposite extreme classitis: so many small classes that each does little and every caller must learn them all. The test is the ratio: how much the module hides for how little it asks you to know.

Key idea

A good interface is much smaller than what it hides. A helper that every caller must combine correctly has moved the code, not the decision.

0:45 – 1:00

What crosses the boundary

A boundary is also a promise between two sides. Names and types are the visible part. The rest is meaning: which units, which time zone, which text format, whether the edge value is included, who converts. When the two sides assume different meanings, both sides can be correct on their own and wrong together.

Case: Mars Climate Orbiter, 1999

A ground program called SM_FORCES, run by the spacecraft team at Lockheed Martin Astronautics, wrote thruster data into a file (the AMD file). The project's Software Interface Specification said the impulse values must be in newton-seconds. The program wrote them in pound-force seconds. JPL's navigation software read the file as the specification said, in newton-seconds, and so underestimated the effect of each thruster firing by a factor of 4.45. The small errors added up over the nine-month cruise. At arrival the orbiter was about 170 km lower than planned, and it was lost on 23 September 1999.

The investigation board named the units error as the root cause and listed eight contributing causes, including verification that did not cover the ground software and poor communication between project teams. It was not "just a units bug": the process around the interface did not catch it for months.

AfterHours has the same kind of boundary, in miniature. Every value that crosses policy.cancellation() has a meaning that could be read two ways:

At the boundaryCould be read asWhat we wrote down
starts_at, nowUTC or festival time? Text or a time object?Festival local time, as naive datetime objects. Callers parse text first.
the notice period24 what? Hours, minutes?timedelta(hours=24): the unit travels with the number.
the deadlineIs cancelling allowed at the deadline?Allowed while now < deadline; at exactly 24 hours before, refused.
cancel_until in the API2026-10-08T20:00 or 2026-10-08T20:00:00?Same text format as starts_at: minutes, no seconds.

Types are guardrails. A signature like cancellation(starts_at: datetime, now: datetime) -> Cancellation says more than can_cancel(starts_at: str, now: str, hours: int) -> bool: no format to guess, no unit to forget, and a result with a name for each part. Python does not check these hints while the program runs; a type checker such as mypy checks them before it runs, and they tell every reader, human or agent, what the boundary expects. What a type cannot say (festival time, the edge value) goes in the docstring, and a test pins it.

Agent-off drill (5 minutes, no laptop)

A teammate adds a mobile API. It calls the policy module like this:

now = datetime.now(timezone.utc).replace(tzinfo=None)   # "strip the zone"
answer = policy.cancellation(event_start, now)

Festival local time is two hours ahead of UTC. The escape room starts Friday 20:00 festival time, so cancelling closes Thursday 20:00. Maya taps Cancel on Thursday at 21:00 festival time. What does the mobile API answer, and for how long is the rule wrong? Write the answer, then one change to the boundary that would have stopped it.

Answer

At 21:00 festival time the server's UTC clock reads 19:00. With the zone stripped, the policy compares 19:00 with a 20:00 deadline and says allowed: Maya's cancellation goes through an hour after it should have been refused. Every cancellation between 20:00 and 22:00 festival time on the deadline day is wrongly allowed. Both sides did what their own code says, as in 1999.

The policy cannot catch this by looking at the value it receives: once .replace(tzinfo=None) has stripped the zone, 19:00 UTC and 19:00 festival time are the same naive object. Stripping the zone destroyed the information needed to notice. What works: make the boundary accept only zone-aware times and reject naive ones, converting to festival time inside the policy; or keep naive festival time and make one function, clock.now(), the only allowed source of "now" (the kit has one), checked in review; and write the convention in the docstring and in a test. Week 10 comes back to UTC and local time.

Key idea

An interface is a promise about meaning: units, zones, formats and edges. Write them down where the boundary is, make the types carry what they can, and test the rest.

1:00 – 1:15

Legible to whom?

A common claim is that code a new teammate can change safely is also code an agent can change safely. It is plausible. A new teammate and an agent both start from nothing, have to find the places before they can edit them, and learn the codebase from what they read. For an agent, what it reads fills its context (Week 3). If a rule lives in one module, there is less to find and less to miss, and a small test file for that module gives fast feedback.

It is also a hypothesis, and so is its usual yardstick, "fewer files to read". Agents read quickly and search well; a small tangled codebase may cost them little. So we tried it once.

We gave Codex (the gpt-6-astra model) the same request on two copies of AfterHours with the same behaviour and the same 33 characterization tests: the tangled kit, and the modular version with the old rule. The modular copy also had five unit tests for policy.py (38 tests in all), and the agent could read those too. The request stated the new rule and its message and said to keep all other behaviour the same. Two fresh runs on each copy. Afterwards we ran 5 hidden spec tests, which the agent never saw, against each result.

What we saw, in order of surprise:

  • Reading did not shrink. In both codebases the agent read AGENTS.md, the README, the main code and several test files before editing: 11 to 15 files in the tangled one, 15 to 17 in the modular one. On an app this small it can afford to read nearly everything.
  • The edit shrank. Both tangled runs found every place the rule lived, and each pulled the deadline into a helper function of its own, a small seam. Both modular runs changed the same two lines of policy.py as our reference solution.
  • An interface detail drifted. Both tangled runs rewrote the code that builds cancel_until and changed its format from 2026-10-08T20:00 to 2026-10-08T20:00:00. The web page shows both the same way, and no characterization test pinned the format, so the agents' own test runs were green. In the modular runs that code was never touched, so it could not drift.
  • No run weakened or deleted a test. All of them added tests.

So in this observation the modular version did not save reading. It saved edits, and code that is not edited keeps its promises. With two runs each, one model, one prompt and a codebase we designed for exactly this change, treat it as a reason to keep testing the idea, not as proof. The full logs are in lectures/04-boundaries/demo/agent-observation/.

Write the contract (pairs, 4 minutes)

Write the task contract (Week 3) you would give an agent for the 24-hour change, once for each codebase. What can you promise or require in the modular one that you cannot in the tangled one?

Debrief

In the modular codebase you can bound the change: "Only app/policy.py and its tests should change. If anything else needs to change, stop and tell me why." That limit is checkable in the diff (git diff --stat), and a diff that breaks it is a signal worth reading. In the tangled codebase the honest contract is "find every place", which asks for exactly the search that is easy to get subtly wrong. A second useful line in both: "Keep the format of every existing API field", which names the drift above so a reviewer can check for it.

Key idea

Judge a boundary by the behaviour it preserves and the responsibility it contains, not by counting files. "Legible to people, legible to agents" is a hypothesis worth testing on your own code.

1:15 – 1:25

Write the decision down

A boundary is a decision, and the reasons for it disappear first. In a year, someone (or some agent) will look at policy.py and ask why the rule is not simply in the route. In 2011 Michael Nygard proposed a light way to keep the answer: an architecture decision record (ADR), a short text file in the repository, one per decision, numbered and never renumbered. His format has five parts: a title, the context (the forces at play), the decision, its status, and its consequences, where All consequences should be listed here, not just the "positive" ones. He also kept it short: The whole document should be one or two pages long.

This course adds one section Nygard's format does not have: alternatives considered, at least one option you rejected and why. A rejected alternative shows that a choice was made, and tells the next person what not to try again without new information.

Key idea

A boundary without its reasons gets undone by the next person in a hurry. An ADR keeps the context, the choice, what you gave up, and what you rejected, next to the code.

ADMIT ONE · WEEK 5

After class · about 25 minutes

Boundaries over time

The lecture moved one rule behind one boundary. These four short readings are about where boundaries come from, how they go wrong, how to record them, and how to move one safely. Read them before the lab.

R1

Teams leave marks in code

The Mars Climate Orbiter's broken boundary sat exactly between two organisations. Melvin Conway described that pattern in April 1968, in Datamation: organizations which design systems (in the broad sense used here) are constrained to produce designs which are copies of the communication structures of these organizations. Fred Brooks later called the idea "Conway's law" in The Mythical Man-Month, and the name stuck.

Read it both ways. If your team splits into an attendee pair and a door pair, expect an API between their code, and expect the cancellation rule to be copied on both sides unless someone owns it. And if you want a boundary somewhere, somebody has to own each side and talk to the other on purpose. Agents add a twist: each agent session starts without the team's conversations, so whatever is not written down (in AGENTS.md, an ADR, a docstring) does not cross that boundary at all. Week 10 returns to Conway's law with several people and agents working in parallel.

R2

The wrong abstraction

After today, it is tempting to remove every repetition you see. Sandi Metz warns against doing that too early. In a 2016 post she repeats advice from a 2014 talk: duplication is far cheaper than the wrong abstraction, and so prefer duplication over the wrong abstraction. She describes how it happens. Someone extracts shared code into one function. A new need arrives that is almost the same, and the next programmer keeps the shared function: in her words, they alter the code to take a parameter, and then add logic to conditionally do the right thing based on the value of that parameter. Then: Another new requirement arrives. Programmer X. Another additional parameter. Another new conditional. Loop until code becomes incomprehensible.

Her way out: When dealing with the wrong abstraction, the fastest way forward is back. Inline the shared code back into each caller, delete what each caller does not need, and look again.

So how is today's policy.py different from check_time? It groups code by what changes together and who changes it (the organisers' time rules), not by what looks alike. check_time merged three rules because all three compared times. When booking, cancelling and the door change for different reasons, a shared function has to bend three ways at once. Parnas's question is the test: which decision does this module hide, and would one likely change stay inside it?

R3

An ADR from AfterHours

This is the full record behind the card in class. It is the reference ADR for the lab (solutions/core/docs/adr/0001-cancellation-rule-in-policy-module.md). Notice what it keeps that the code cannot: why, what else was tried, and what got worse.

0001. The cancellation rule lives in one policy module

Status: accepted · Date: 2026-10-01 · Decided by: Ana (product lead this week), with Jo (implementer) and Wei (verifier)

Context. The organisers asked for cancellations to close 24 hours before an event starts, instead of at the start. They have changed time rules before (the door opening time) and said they may want a longer notice for workshops next year. Today's rule is written down in seven places in three files: the check and its message in the cancel route, the deadline in the booking confirmation, two SQL expressions in the My-bookings query, the help text on the attendee page, and AGENTS.md. Making the change in place needed 8 edits in 3 files, in Python, SQL, HTML and Markdown. One tempting SQL shortcut, SQLite's datetime(starts_at, '-24 hours'), returns 2026-10-08 20:00:00 (a space, not a T), and comparing that text with our stored format gives the wrong answer whenever the deadline and "now" fall on the same day.

Decision. We will keep the cancellation rule in app/policy.py, behind one function: cancellation(starts_at, now) -> Cancellation(allowed, deadline, reason). Callers pass festival local time as naive datetime objects; they parse stored strings first and never compare times for this rule themselves, in Python, SQL or HTML. The deadline is starts_at − 24 hours and is exclusive: cancelling is allowed while now < deadline. The API reports it as cancel_until in the same text format as starts_at, and the page shows that value instead of describing the rule in words. We made the move first as a refactor with no behaviour change, then changed the rule in a second commit.

Alternatives considered. Edit the rule where it is. Rejected: cheapest today, but the next change costs the same again, and the SQL, the page and the docs can drift apart unnoticed. Store the notice period per event in the database. Rejected for now: the organisers want one festival-wide rule; revisit if they ask for per-event notice (a schema change and an interface change). Read the notice period from an environment variable. Rejected: a rule change would not show up in a code review or a test diff, and each server could run a different rule.

Consequences. Changing the notice period is now a two-line change in one file, with fast unit tests. A different kind of rule (48 hours for workshops only) needs information the interface does not take today, so it will change the interface and its three callers. One more module to learn, and callers must parse starts_at first. My bookings decides can_cancel in Python, row by row, which is fine at festival scale. The tests that pinned the old rule were retired in the rule-change commit, on purpose. Not addressed: the door page's "expected" count still includes cancelled reservations; it needs its own decision.

Three habits make ADRs useful. Write one when a decision is expensive to reverse or will surprise the next reader, not for every choice. Name a person who owns it, as the course rule asks for every consequential decision. And point to the ADR from the code it explains (the reference solution's policy.py names ADR 0001 next to the rule), so a reader, or an agent reading the file, finds the reason where the question arises.

R4

Make the change easy, then make the easy change

On 25 September 2012 Kent Beck posted: for each desired change, make the change easy (warning: this may be hard), then make the easy change. It is the plan for Part A of the lab, and it has a precise meaning in terms of tests.

Step 1, make the change easy, is a refactor: it changes the structure of the code without changing its behaviour. You move the rule into policy.py and route every caller through it, and the rule stays exactly what it was. The evidence is that every existing test still passes and none of them was edited. It is evidence, not proof: tests only see what they check, so you also read the diff for behaviour no test covers. The kit's characterization tests record what the app does today, right or wrong. Michael Feathers puts their purpose as to document your system's actual behavior, not check for the behavior you wish your system had.

We learned the limit of that evidence on this very lab. An independent review of an earlier draft created an event starting at 20:00:30. The kit echoed that time back as the cancellation deadline; our reference refactor rounded it to 20:00, and all 37 tests stayed green because none of them used seconds. We fixed the kit rather than the test count: event times must now be whole minutes (a characterization test pins that), so the refactor is exact for every time the app accepts.

Step 2, make the easy change, changes behaviour on purpose. Now some tests should fail: the ones that pinned the old rule. You retire them in the same commit as the change, and the new-rule tests go green. A reviewer reading that commit sees the rule change and the test change side by side.

Beck's warning in brackets is real. In the lab, step 1 is most of the work: finding seven places and routing them through one function without changing what any of them does. Step 2 takes a minute. That is the point: the hard part happens once, under the protection of tests that do not move, and the next rule change is cheap.

Keep the two steps in separate commits, and ask the same of an agent. "Refactor with no test changes, show me the green run; then change the rule" is a task contract you can check from the diff alone.

W

Words from today

Module
A part of a program that others use only through its interface, so its insides can change without them.
Interface
Everything a caller must know to use a module: names and types, and also units, time zones, formats and edge cases.
Information hiding
Parnas's criterion: give each module one design decision that is likely to change, and hide it from the others.
Deep module
A module whose interface is much smaller than the work it does for its callers (Ousterhout). A shallow one asks you to learn almost as much as it saves you.
Change amplification
When a seemingly simple change needs edits in many places. The symptom behind today's hook.
Seam
In Feathers's words, "a place where you can alter behavior in your program without editing in that place". In the lab, policy.cancellation() is the seam for the rule.
Characterization test
A test that records what the code does now, right or wrong, so a refactor can show that the behaviour it covers did not change.
Refactor
A change to the structure of code that keeps its behaviour. In this lab it may not edit the supplied characterization or old-rule tests. (Elsewhere, moving an internal interface can mean adapting unit tests that call it; tests of outside behaviour should stay as they are.)
ADR
Architecture decision record: a short file in the repository with the title, context, decision, status and consequences of one decision (Nygard), plus, in this course, the alternatives rejected.
Conway's law
Systems tend to copy the communication structure of the organisations that design them.
