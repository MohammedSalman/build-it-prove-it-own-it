Week 1 · The new shape of the work

Code Is Cheap. Software Isn't.

A coding agent can build a good-looking app in an afternoon. This lecture is about the distance between an app that demos well and a system that keeps its promises, and about the engineer's job in that distance.

90-minute lecture 2-hour lab ~25 minutes of reading after class Starter: AfterHours

By the end of today you can

  • Tell apart "the feature works" and "the system keeps its promise".
  • Trace one request from a tap to a database row, and name the assumption on each step.
  • Draw a race condition as a timeline and state the invariant it breaks.
  • Give an agent a bounded task and check its claims against evidence.
  • Judge a patch by the failure it addresses and the cost it adds, not by whether tests are green.

0:00 – 0:10

The last seat

Meet AfterHours, the platform you will build on all semester. It runs a student festival: three nights of events, each with a limited number of places. We built the first version the way many teams now work. We described the feature to a coding agent, looked at the result, clicked around, and ran the tests.

It looks done. The page is clean. The escape room shows 1 place left. The test suite says 7 passed.

Vote

Tonight at 8 pm, 2,000 students get the link. Do you ship? Raise a hand for ship or hold, and name one piece of evidence behind your vote.

Now Maya and Sam, on two phones, press Reserve at the same moment.

Nothing crashed. No test failed. The app did exactly what its code says. The API now reports that the escape room has "places_left": -1.

About this bug

We planted this defect on purpose so it shows up on cue. It says nothing about any particular model or tool. It is a very common kind of bug, and it slips through review easily when everyone is looking at a demo that works.

Key idea

A working demo is a hypothesis. It shows the software can work. It does not show that the software keeps its promises.

0:10 – 0:20

Follow the promise

Ask what each person now believes. Maya believes she has a place. So does Sam. The room has 40 seats, so someone will be turned away at the door after the app told them they were in.

The code returned success both times. Returning success and keeping a promise are different things. To see where they come apart, follow one request from the tap to the database.

When Maya presses Reserve, her browser sends an HTTP POST request to /api/events/1/reservations with a small JSON body, {"attendee": "Maya"}. FastAPI calls reserve() in app/reservations.py, which does three things in order:

taken = count_reservations(event_id)     # ① check
if taken >= event.capacity:
    raise SoldOut                         #   → HTTP 409 "event is full"
payments.authorize(attendee)              # ② pay (about 300 ms, nothing is charged)
insert_reservation(event_id, attendee)    # ③ save → HTTP 201 Created

Simplified from app/reservations.py. Open the real file in the lab.

The promise, written down

confirmed reservations for an event ≤ its capacity

This is an invariant: a statement that must be true at every moment, for every possible order of events, not only at the end of one test.

0:20 – 0:30

Make the race visible

The app writes a log line at each step, with a millisecond timestamp. This is the real log from the run in Fig 1.1:

21:24:31.734  [Maya] checked: 39 of 40 places taken
21:24:31.734  [Sam] checked: 39 of 40 places taken
21:24:32.040  [Maya] payment authorised (simulated, nothing charged)
21:24:32.040  [Sam] payment authorised (simulated, nothing charged)
21:24:32.042  [Maya] reservation #228 saved
21:24:32.045  [Sam] reservation #229 saved

Each request makes its decision from a count that the other request is about to change. This pattern is called check-then-act. When two actors check and then act, and nothing forces them to take turns, you have a race condition.

The slow payment call makes the race likely, but it does not cause it. With the payment delay set to zero, race.py still oversold 7 of 20 trials on a laptop. The gap between check and save is never truly zero.

Try it on paper (pairs, 6 minutes)

Take six strips: Maya-check, Maya-pay, Maya-save, Sam-check, Sam-pay, Sam-save. Keep each person's strips in their own order and merge them into one timeline. If a check finds the room full, that person gets a 409 and stops.

  1. Find an order that oversells.
  2. Find an order that does not.
  3. How many orders are possible, and how many oversell?
Answer to question 3

There are 20 orders: pick which 3 of the 6 time slots belong to Maya. Only 2 keep the promise, where all of one person's steps come before all of the other's. The other 18 oversell. When two people press within the same 300 ms, you get one of those 18.

Why did the tests miss it? Open tests/test_basics.py. Every test sends one request, waits for the answer, then sends the next. Tests like that only ever produce the two safe orders. The dangerous orders need two requests in flight at once, and no test in the suite does that.

Agent-off drill (2 minutes, no laptop)

Two places are left. Three people press Reserve in the same instant. With the starter code as it is, how many reservations exist afterwards? Write down your prediction. You will check it in the lab with python scripts/race.py --people Maya,Sam,Lee --capacity 2.

0:30 – 0:45

Ask an agent, check the evidence

Agents are good at this kind of investigation. They read every file on the path, list assumptions, and suggest fixes. They also write fluently and confidently, which makes their output easy to believe. So we give the agent a bounded task, and we treat its answer as a set of claims to check.

Task contract
Goal
Find out whether AfterHours can confirm more reservations than an event's capacity, and why.
Context
Small FastAPI + SQLite app. Read AGENTS.md first. The promise: confirmed ≤ capacity.
Limits
Investigate only. Do not modify any file.
Deliver
The code path with file:line references. Every assumption. Whether the promise breaks, with evidence, marking what you ran versus what you inferred. The smallest repair, not applied, and what it would not fix.
Stop when
You have evidence, or you are blocked. If blocked, say what blocked you.

We gave this contract to a real coding agent (Codex CLI with the gpt-6-astra model) on a throwaway copy of the starter. Its full, unedited answer is in lectures/01-code-is-cheap/demo/agent-investigation.md. Here is what it claimed, and what we did with each claim.

Reading R7 comes back to this.

0:45 – 1:10

Three patches, one question

Three facts you need before judging the patches
  1. Requests really do run at the same time. FastAPI runs each plain def handler on a pool of worker threads, so Maya's and Sam's requests execute side by side.
  2. A transaction groups steps. The statements between BEGIN and COMMIT succeed or fail together. BEGIN IMMEDIATE also takes the database's write lock right away, before the first read. Plain BEGIN waits until the first write.
  3. SQLite allows one writer at a time, for the whole file. Another connection that wants to write waits for the lock (here for up to 5 seconds, then it fails). Readers can keep reading, because the starter uses SQLite's WAL mode.

Here are three candidate fixes. All three keep the test suite green. The diffs below are shortened; the full versions are in lectures/01-code-is-cheap/patch-cards/.

Debrief: what the checks say (open after you vote)

We ran three checks against the starter and each patch. race.py gives one last place to two people pressing at the same instant, 10 times. rush.py has 20 people book 20 different events at once. These timings come from one laptop (classroom gate off). Yours will differ in the decimals, not in the pattern. Patch C's rush result was the same on three repeated runs.

Patch A guards the button. It blocks a second click while the first request and the page refresh are still on their way. After that, if places remain, the refreshed button is enabled again, and another click can book a second place. One person booking twice is a real problem, but a different one. Maya and Sam are on two phones and never touch each other's buttons, so the race is untouched.

Patch B treats the first check as a hint. After payment it takes the database's write lock, checks again, and saves, all within about a millisecond. The second request waits for that millisecond, sees the room is full, and gets a 409.

Patch C, the agent's suggestion, also keeps the promise. The agent itself warned that it would increase contention; rush.py turned that warning into a number. It holds the write lock for the whole payment, and SQLite has one write lock for the entire database. Every booking at every event waits in a single line: at most about three bookings per second for the whole festival. When a request waits more than 5 seconds for the lock, SQLite gives up and the user sees an HTTP 500.

Key idea

A check aimed at the bug you feared can miss the damage your fix causes. race.py passed Patch C. Only a second, different check showed the cost. Correct for capacity is not the same as fit for a festival rush.

Patch B is the one to ship, and it still leaves work, most of it for later weeks:

  • Sam's payment was authorised, but he got no place. A real system must release that hold (Week 6).
  • Maya can still reserve twice from two browser tabs. Nothing makes one person's reservation unique (Week 6).
  • If a lock wait ever passes 5 seconds, the user gets a 500 instead of a clear message. No later week covers this one: it stays open as a production-hardening task for your team.
  • Anyone can reserve under someone else's name (Week 8).
1:10 – 1:25

The engineering loop

Look back at the last hour. We worked out what the user was promised and wrote it down as an invariant. We delegated an investigation, inspected the agent's claims, verified three patches with two different checks, and decided what could be released. Writing code was the smallest part of that work.

This loop is the course. Each week strengthens one part of it, and the AfterHours project uses every part. The course has one rule:

The course rule

Every important claim about the software needs evidence. Every consequential decision needs an accountable human.

How you will work

  • Teams of four build AfterHours for a festival identity you choose. Roles rotate weekly: product lead, implementer, verifier, release steward.
  • Agents are allowed and expected. Disclose meaningful help. You own every line and every claim you submit.
  • You are graded on evidence, not on lines of code or prompts. An evidence packet traces each decision: requirement → decision → change → check → result.

ADMIT ONE · WEEK 2

After class · about 25 minutes

Why this course exists

The lecture stayed with one bug. These seven short readings give the bigger picture behind it. Read them before the lab.

R1

Why code got cheap

Programming has been automated before. The first programmers wrote machine instructions by hand. Then assemblers and compilers took over that work, and each step drew the same doubt. Grace Hopper, recalling her first compiler in a 1987 lecture, was reported as saying: I had a running compiler and nobody would touch it. They told me computers could only do arithmetic. John Backus, whose team built FORTRAN in the 1950s, wrote later that our claims that we would produce efficient object programs were disbelieved.

Coding agents are the newest step, and a big one: they write, run, and fix code across many files. Like every step before them, they leave you with the questions of what the program should do and how you know it does it.

R2

Essence and accident

In 1986 Fred Brooks split the difficulties of software into two kinds. In his words: Following Aristotle, I divide them into essence, the difficulties inherent in the nature of software, and accidents, those difficulties that today attend its production but are not inherent. The essence, he wrote, is a construct of interlocking concepts: data sets, relationships among data items, algorithms, and invocations of functions. His claim was specific: no single development would bring even a tenfold improvement in productivity, reliability, or simplicity within a decade, because the big past gains, such as high-level languages, had mostly removed accidental difficulty, and what remained was mostly essential.

The essential part stays with you, even when an agent helps you think it through. In AfterHours, deciding that the last place goes to exactly one person, and what happens to the other person's payment, is essential. Writing the SQL is accidental.

R3

How much autonomy?

AI coding tools sit at different points on a scale. Autocomplete suggests a line. A chat assistant writes a function you paste in. An agent in your editor edits files and runs tests while you watch. A background agent works on its own and opens a pull request. Several agents can work in parallel. In a mid-2025 talk, Andrej Karpathy called this the autonomy slider: you choose how much autonomy to hand over, task by task.

There is no single right setting. Renaming a variable across a project can go far to the right. Changing how payments are captured should stay to the left, with a human reading every step. Choose per task, and choose on purpose.

R4

The bottleneck moved

When writing code was slow, it limited how fast a team could ship. Agents widened that part of the pipe. For many teams the narrowest part is now verification: reading diffs, running the right tests, trying the edge cases, asking whether the change does what the user needs. Whether that is true for your team is something to measure, not assume (Week 11). This course spends most of its time on specifying and verifying because that is where the narrow part tends to move.

R5

When vibe coding is fine

On 2 February 2025, Andrej Karpathy named a style of work: There's a new kind of coding I call "vibe coding", where you fully give in to the vibes, embrace exponentials, and forget that the code even exists. He accepted every change without reading the diffs, and he was clear about where it belonged: It's not too bad for throwaway weekend projects. The term spread much faster than that limit.

AfterHours takes commitments from real people and will be maintained all semester, so it sits in the top-right corner. A weekend toy sits in the bottom-left, and vibe coding it is fine. Trouble starts when something built in the bottom-left quietly moves up or to the right, and nobody changes how it is built.

R6

Feeling fast, being fast

How much do AI tools speed developers up? Asking developers is not a reliable way to find out. In an early-2025 randomised trial by the research group METR, 16 experienced open-source developers worked on 246 real tasks in projects they already knew well, with AI tools allowed on some tasks and not on others.

Read this result carefully. It covers experienced developers in large projects they knew well, using early-2025 tools, and the authors say it does not show that AI fails to help most developers. In February 2026 METR reported a follow-up whose raw numbers point toward speedups, but METR itself calls that data an unreliable signal, partly because many developers were no longer willing to work without it. The lasting lesson is the gap between the first two bars and the third. How fast you feel is weak evidence about how fast you are. In this course, when a workflow question matters, we measure.

R7

A sign asks, a fence decides

Case: Replit, July 2025

Jason Lemkin, founder of SaaStr, was building an app with Replit's AI agent and had declared a code freeze. He reported that the agent deleted his project's production database anyway, and then wrongly told him a rollback was impossible. The rollback worked. Replit's CEO, Amjad Masad, called the deletion unacceptable and should never be possible, and Replit began separating development and production databases automatically.

A code freeze written in a chat, a prompt, or an AGENTS.md file is a sign. Signs are useful, and agents usually follow them, but "usually" is not good enough for something you cannot undo. For those actions, build a fence: separate development and production databases, credentials the agent never sees, a sandbox that blocks the action outright. In today's investigation, "do not modify files" was a sign, and the blocked network port was a fence.

W

Words from today

Invariant
A statement about the system that must be true at every moment, such as confirmed ≤ capacity.
Race condition
A bug whose result depends on the timing or order of concurrent actions.
Check-then-act
Deciding from something you read, then acting later as if it were still true.
Transaction
A group of database steps that succeed or fail together. BEGIN IMMEDIATE takes the write lock at the start; plain BEGIN takes it at the first write.
Write lock
Permission to change the database. In SQLite only one connection holds it at a time, for the whole file. Other writers wait (here up to 5 seconds, then fail); in WAL mode, readers carry on.
HTTP 201 / 409 / 500
Created · conflict (here: the event is full) · the server failed.
Task contract
A delegated task written with its goal, context, limits, deliverables, and stopping condition.
Evidence packet
requirement → decision → change → check → result, for one decision.
