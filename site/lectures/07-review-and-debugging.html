Week 7 · Inspect

Review and Debugging at Agent Speed

An agent can open a 450-line pull request in an afternoon, with every test green. This lecture is about reading it with a method, and about what to do when something slips through anyway: write down hypotheses, run the experiment that tells them apart, and let git find the commit.

90-minute lecture 2-hour lab ~25 minutes of reading after class Loop: Inspect Kit: PR #14 and a 20-commit history

By the end of today you can

  • Review a large pull request in order of risk, starting from its claims and its tests.
  • Recognise six kinds of problem that a green test run does not show.
  • Keep a hypothesis log and design an experiment that tells two hypotheses apart.
  • Use git bisect run to find the commit that changed a behaviour, and say what it needs from you.
  • Point to where evidence disappears on a request's path, and put it back with request ids and counts.

About this pull request

It says nothing about any particular model or tool. Each kind of problem also turns up in code written by people.

Key idea

A green check says the tests that still exist passed. Review asks what the tests no longer cover, and what changed besides the code you were told about.

0:15 – 0:35

A review method

Read 455 lines top to bottom, file by file, and your attention runs out somewhere in the middle. The diff lists files in alphabetical order, which has nothing to do with risk. A method puts your freshest attention on the lines most likely to hurt someone.

1 · Claims and tests before code

Start with the description and write down each claim it makes: "a problem in the notification step can never block a booking", "26 tests pass". Each claim is something to check. Then look at the tests, because they show what the author thinks is covered. Three commands give you the shape of the change:

git diff --stat 4ac8467 b7675a2                       # every file, lines changed
git diff --stat 4ac8467 b7675a2 -- tests/             # what happened to the tests
git diff --diff-filter=D --name-only 4ac8467 b7675a2  # files that were deleted

For every deleted test, ask two questions: what did it check, and what checks that now?

2 · Read in order of risk

The tiers come from one question per hunk: if this line is wrong, who gets hurt, and would anyone notice? Transactions and promises, error handling, changed defaults, secrets and calls into libraries go first. UI and docs go last, and for docs you check one thing: that they claim only what the code does.

3 · A checklist, so you don't rely on memory

  • Transactions and promises. What moved into or out of a transaction? Which invariant could this break?
  • Every except. What is caught, what happens next, and who finds out?
  • Every changed default. Who relied on the old value? Does the description mention it?
  • Secrets. Tokens and passwords in code, tests or config, including as default values.
  • Calls into libraries. Does every function exist in the pinned version? Did anyone run this line?
  • Work per request. Queries inside loops. Ask for a measurement before calling it slow or fine.
  • Observability. If this fails in production, which log line or number tells you?

The full checklist, with the commands, is review-checklist.md in the lab kit.

4 · Ask for small pull requests

Small changes get better reviews, and the evidence supports the habit. At Google, in about 9 million changes from 2014 to 2016, the median change modified 24 lines, over 35% touched a single file, and the median time for the whole review process was under 4 hours (Sadowski et al., 2018). SmartBear's study at Cisco, 2,500 reviews done with SmartBear's own review tool, advised reviewing at most 200 to 400 lines at a time, under about 500 lines an hour, for no more than 60 to 90 minutes. It is a vendor study that reports little of its method, so treat its numbers as a rule of thumb.

Reviews are also less about bugs than people expect. At Microsoft, finding defects was the top reason developers gave for reviewing, yet only 14% of the review comments in the researchers' sample were about defects, and developers named understanding the change as their main challenge (Bacchelli & Bird, 2013). PR #14 is 455 changed lines with four purposes: a waitlist, a notifications rework, a test rewrite and new settings. A fair first comment is "please split this into four".

5 · AI reviewers are a signal

An AI reviewer can go through a long diff quickly, and it may flag something like a swallowed exception. It may also miss parts of a large change, or be confidently wrong, and it cannot be accountable for the merge. Treat its comments as more findings to check, the way you treated the agent's claims in Lecture 1. A person approves the change, and that person owns the approval.

Debrief: what a reviewer should have said (open after you discuss)

A is a swallowed exception, and a blocker. app/reservations.py:72–73: except Exception followed by log.debug. A DEBUG line does not appear at the app's normal log level (INFO, and WARNING after patch B), so any failure here stays invisible unless someone sets AFTERHOURS_LOG_LEVEL=DEBUG, a setting patch B adds. The booking has already committed, so the user gets 201 and "You're in!" with no confirmation. The hunk also moves the outbox write out of the booking's transaction, which breaks the team's own promise in AGENTS.md: every booking puts exactly one confirmation in the outbox. The reason given does not hold up. The outbox already keeps mail problems away from bookings: a separate mailer sends the rows later. That design has a name, the transactional outbox: store the message in the same transaction as the change, and let a separate process send it. Ask: put the call back inside the transaction, or at the very least log the failure at ERROR with its traceback.

B is a silently changed default, and a major finding. app/settings.py:7, used at app/main.py:20. The app logged at INFO; now it logs at WARNING unless someone sets the variable. Every "checked", "saved" and "queued" line disappears from production logs. The description does not mention it, and it has nothing to do with a waitlist. Ask: keep INFO, or explain the change in the description.

C is a deleted test, and a blocker. The deleted file held the only tests that booked through the API and then looked in the outbox. The new tests check the text of a message; none checks that a message is queued at all. The count went up while the coverage of the promise went to zero. AGENTS.md says "Never weaken or delete a test to make it pass". A rule in AGENTS.md is a sign; a CI step that fails when a pull request deletes a test file would be a fence (Lecture 1, R7).

Put A and C together and you have a failure that nobody will see and no test will catch. The other three problems (the query per row, the secret, the function that does not exist) are yours to find in the lab.

Key idea

Review the claims and the tests first, then the code in order of risk. The riskiest lines are rarely the longest part of a diff.

0:35 – 0:55

Debugging as an experiment

Incident · Thursday 8 October, 10:40

Five people at the info desk this morning said they never got a booking confirmation. They all booked last night or this morning. The app told them "You're in!" and they are on the door list. Has something changed?

What the team knows: the API answered 201; the event counts went up; CI is green on every commit. For one of the affected bookings, the server log has exactly one line:

INFO:     127.0.0.1:63121 - "POST /api/events/3/reservations HTTP/1.1" 201 Created

The fastest move is to paste the report into an agent and ask it to fix the problem. It may well produce a plausible change, perhaps a retry around sending. The tests would tell you nothing about it: they are green now, and none of them looks in the outbox. A fix chosen before a diagnosis is a guess, and nothing would tell you whether it worked.

Reproduce first, with explicit starting conditions

Before any theory, make the failure happen on demand. Given a fresh database with Board Game Night at 23 of 60 places taken, when Maya books through the API, we expect 201 and one message to maya@example.org in the outbox. Actually: 201, 24 places taken, and an empty outbox. The lab kit turns exactly this into a script, check_confirmation.py, that exits 0 when the confirmation arrives and 1 when it does not.

Then hypotheses, each with a prediction

A hypothesis is a possible cause that predicts something you can observe. Write it down before you run anything, together with what you expect to see if it is true. Andreas Zeller, who wrote a textbook on this, puts the goal of a prediction precisely: Ideally, the prediction would distinguish the hypothesis from likely alternatives.

The event count went up, so the booking exists: H1 is out. The outbox has no new rows at all, so nothing was queued, and there is nothing to deliver late or send to the wrong address: H2 and H3 are out. Two remain. Either the confirmation step never runs (H4), or it runs, fails, and the failure is hidden (H5).

A discriminating experiment

An experiment discriminates when its possible results differ between the hypotheses still standing. Reading the code can tell you which one is more likely, but it cannot show what happened on this request. Trying a fix changes the system instead of observing it. You want one run of the real request path whose outcome sends you down one branch or the other.

Agent-off drill (5 minutes, pairs, no laptop)

H4 and H5 are left. Design one experiment whose result is different under each. Write the exact thing you would run, what you expect to see if H4 is true, and what you expect if H5 is true. You may use anything a developer has: the app, its settings, a Python prompt, the log, the database.

Two good answers

Turn the logging up and replay one booking. Start the app with AFTERHOURS_LOG_LEVEL=DEBUG, book once, and search the log for that booking's request id. H4 predicts no trace of a confirmation attempt. H5 predicts an error line.

Or tag the path. Add a temporary log line at WARNING just before the confirmation step and another in the except block, then book once. H4 predicts neither line appears for that request id; H5 predicts both.

A weaker cousin: call the queueing function directly from a Python prompt. If it raises, you have learned that the function is broken in isolation, which is useful. You have not learned that the request reached it, so on its own it does not separate H4 from H5.

The DEBUG run takes under a minute. In the lab you run it, and its result names the line.

Key idea

A fix should follow a discriminating experiment. If no possible result of an experiment could change your mind, it is not an experiment.

0:55 – 1:10

Let git do the search

Hypotheses tell you what kind of failure you have. History can tell you when it started. You know a good point: on Monday evening Priya booked a place and saw the confirmation in the outbox, and that deploy is tagged v0.2. You know a bad point: today's HEAD. Between them are 16 commits. You could read all 16 diffs, or test the one in the middle and throw away half of the suspects.

Each test halves the suspects, so 16 commits need 4 tests, 1,000 commits need 10, and a million need 20. The work grows with the logarithm of the history's length, which is why bisect stays useful in a repository with years of commits. Git runs the search for you:

git bisect start HEAD v0.2                                # bad first, then good
git bisect run python ../incident/check_confirmation.py   # git tests, you wait
git bisect reset                                          # back to where you were

With run, git checks out a commit, runs your command and reads its exit code. The rules come from git's documentation: 0 means good; 125 means this commit cannot be tested, so skip it; any other code from 1 to 127 means bad; any other code at all stops the bisect.

What bisect needs from you

  • A good commit that you checked. "Nobody complained on Tuesday" is not a check. On Monday Priya booked a place and looked in the outbox: that is.
  • A deterministic check. Same commit, same answer, every time. A flaky check sends bisect into the wrong half, and it never comes back.
  • A monotonic check. Good before the culprit, bad after it: the answer flips exactly once. A check that needs a feature older commits don't have will fail there for another reason. Make it exit 125 on those commits instead.
  • A clean working tree. Git checks out other commits under your feet. Commit or stash your experiments first.
  • A check you have run at both ends. Bisect trusts your command completely. If the check cannot run, say because of a typo in the script's path, Python exits with an error code that git counts as bad, and bisect confidently names the first commit after the good one. We tried it: that is exactly what happens. (A command that does not exist at all behaves differently: git 2.50 stopped with an error.)

The kit's check was written to these rules. It uses a fresh temporary database on every run, never reuses compiled Python files from another commit, and exits 125 if the booking itself fails, because that is a different problem. The real session starts like this:

$ git bisect start HEAD v0.2
$ git bisect run python ../incident/check_confirmation.py
Bisecting: 7 revisions left to test after this (roughly 3 steps)
[4fcce69…] waitlist: join a full event; show waitlist counts (#14)
running 'python' '../incident/check_confirmation.py'
GOOD  booking answered 201; outbox holds 1 message(s): [('maya@example.org', "You're in: Board Game Night")]
Bisecting: 3 revisions left to test after this (roughly 2 steps)
…

The lab takes it from there.

Agent-off drill (4 minutes, pairs, no laptop)

Commit 0 is good and commit 16 is bad. Your partner secretly picks the first bad commit. Find it by asking only "is commit k good or bad?", and count your questions. Then: how many questions would you need for 100 commits? For 5,000?

Answers

Four questions for 16 commits, if you always ask about the middle one. 100 commits need 7 questions, because 27 = 128 is the first power of two at or above 100. 5,000 need 13 (213 = 8,192). If you asked about commits one by one from the start, you could need up to 16, 100 or 5,000.

Key idea

Bisect finds where the behaviour changed. It does not tell you why nobody noticed. For that, go back to the review: which commit made the failure silent, and which made the tests blind to it?

1:10 – 1:25

Where evidence disappears

Nothing in the log looked wrong. That was true, and it was the problem. Here is the log of one booking on Monday's deploy, v0.2:

22:40:21.142 [685b125a] [Maya] checked: 23 of 60 places taken
22:40:21.452 [685b125a] [Maya] payment authorised (simulated, nothing charged)
22:40:21.454 [685b125a] [Maya] reservation #228 saved
22:40:21.454 [685b125a] [Maya] confirmation #1 queued for maya@example.org
22:40:21.456 [685b125a] POST /api/events/3/reservations -> 201 in 315 ms
INFO:     127.0.0.1:63113 - "POST /api/events/3/reservations HTTP/1.1" 201 Created

And the same booking on Thursday's HEAD:

INFO:     127.0.0.1:63121 - "POST /api/events/3/reservations HTTP/1.1" 201 Created

Both are real runs of the lab repository.

On Monday every line from the app carries a request id in brackets, 685b125a. A small piece of middleware (commit 6c6f942) creates the id when a request arrives, puts it on every log line the request causes, and sends it back in an X-Request-ID header. One search pulls one booking's story out of a busy log, and a user or a door scanner can quote the id from the response. On Thursday the app writes nothing at all. The only line comes from uvicorn, the web server around the app.

  1. The except block. An exception is the most useful evidence a program produces: what failed, where, and often why. except Exception followed by a DEBUG line throws it away.
  2. The log level. A level is a filter. WARNING keeps warnings and errors and drops everything below them. Changing the default changed what production can tell you, for every line in the app at once.
  3. No number. The app promises one confirmation per booking, and nothing counted either. A two-line query comparing Wednesday's bookings with Wednesday's outbox rows would have shown 0 of N on Wednesday evening, hours before the first complaint.

While building the lab we found a fourth gap, in the team's own middleware. When a request crashes with HTTP 500, the response goes out without the X-Request-ID header, and the middleware never writes the line that says how the request ended. Lines logged before the crash keep their id; the ending, the most important part, is missing. The client has no id to quote. It is worth checking in your own product.

Put the evidence back

  • Every request gets an id. Every log line carries it. The response returns it, including error responses.
  • A failure is either raised, or logged at ERROR with its traceback and the request id. It is never both caught and quiet.
  • If you truly must carry on after an error, log it where it will be seen and count it.
  • Count what you promise: bookings against confirmations, places taken against capacity. A promise you can count is a promise you can watch.
Key idea

Logs are evidence only if failures write to them. Give every request an id, log failures where they will be seen, and count what you promise.

ADMIT ONE · WEEK 8

After class · about 25 minutes

Reading code you did not write

The lecture stayed with one incident. These four short readings are the ideas behind the method: why debugging costs more than writing, why it works as a science, what happens when code arrives faster than understanding, and why reviewers run out of attention. Read them before the lab.

R1

Twice as hard

In The Elements of Programming Style (second edition, 1978), Brian Kernighan and P. J. Plauger wrote: Everyone knows that debugging is twice as hard as writing a program in the first place. So if you're as clever as you can be when you write it, how will you ever debug it? Shorter paraphrases circulate as "Kernighan's law"; the words above are the book's.

The "twice" is a rule of thumb. The argument survives without it: code is read and debugged far more often than it is written, so write it for the person who will debug it. With agents the argument gets stronger. Code arrives at the speed of generation, from an author you cannot later ask what it meant. When an agent hands you something dense and clever, ask for the plain version: in a review comment, in your AGENTS.md, in your task contract.

Plain is necessary, and it is not sufficient. The line that caused this week's incident reads perfectly well. What it lacked was evidence that anyone had run it.

R2

Debugging is a science

Andreas Zeller's textbook Why Programs Fail (second edition, 2009) treats debugging as the scientific method applied to a program. Its chapter "Scientific Debugging" lays out the steps: observe a failure; invent a hypothesis as to the failure cause that is consistent with the observations; use the hypothesis to make predictions; test them by experiments and further observations, refining the hypothesis when the predictions hold and creating an alternative when they don't; and repeat until the hypothesis can no longer be refined.

Zeller's practical advice is to make the process explicit and keep a logbook: write down all hypotheses and observations. The logbook is the hypothesis log from the lab. It makes you commit to a prediction before you see the result, so you cannot quietly reinterpret the result afterwards. It also lets you stop and pick up again tomorrow, or hand the problem to a teammate with everything you have ruled out.

Narrowing can be automated. Zeller and Ralf Hildebrandt's delta debugging (2002) shrinks a failing input automatically. In their case study, a Mozilla crash that took 95 user actions to reproduce came down to 3 relevant ones, and 896 lines of HTML came down to the single line that caused the failure. Zeller had earlier applied the same idea to changes between a working and a failing version, in a 1999 paper with a title every developer recognises: "Yesterday, my program worked. Today, it does not. Why?" git bisect narrows the same way over history, one commit at a time.

R3

Comprehension debt

Jason Gorman, a software developer who writes the Codemanship blog, has used the term comprehension debt for AI-generated code since 2025: When teams produce code faster than they can understand it, it creates what I've been calling 'comprehension debt'. Addy Osmani described it in 2026 as the growing gap between how much code exists in your system and how much of it any human being genuinely understands.

Like technical debt, it is paid with interest, and usually at the worst moment: during an incident, when you need to understand the code fastest. PR #14's six commits add 399 lines and span about 90 minutes. On Thursday morning the team had to understand notify.py under pressure, which cost far more than it would have during review.

This course builds in ways to pay it down: reviews that read for understanding (the main challenge reviewers name, as Bacchelli and Bird found), practice defences where you explain a path unaided, tests you derived from requirements (Week 5), and asking agents for smaller, plainer changes. Each one keeps the second curve closer to the first.

R4

Review fatigue

Attention runs out, and size makes it run out faster. SmartBear's study at Cisco looked at 2,500 reviews covering 3.2 million lines of code over 10 months. The number of defects found per thousand lines fell steeply once more than about 200 lines were under review at once, and its authors concluded: 200 LOC is a good limit; 400 is the absolute maximum. They also reported that performance drops after 60 to 90 minutes of reviewing, and that above 1,000 lines an hour a reviewer is probably not looking at the code at all. Remember that this is a vendor studying its own tool.

Independent research points the same way. At Microsoft, the rate of useful feedback in reviews fell as the number of files in a review grew, noticeably from about 20 files (Czerwonka, Greiler and Tilford, 2015). In three open-source projects, components with more changes that were approved without any discussion had more defects after release (McIntosh and colleagues, 2014). That is a correlation, and it does not prove that discussion prevents defects. It does describe what a bare "LGTM" is worth.

Agents raise the volume of code while the number of reviewers stays the same. The countermeasures are the ones from class: small pull requests with one purpose each; the author, human or agent, stating what was run; review sessions under an hour; a checklist; AI reviewers as extra signal; and the right to say "split this" without apology.

W

Words from today

Code review
Reading someone else's change before it merges, to decide whether to accept it and to understand it.
Risk-ordered reading
Reading a diff's riskiest hunks first (transactions, errors, defaults, secrets, library calls) and the UI and docs last.
LGTM
"Looks good to me": an approval. A useful approval says what was checked and on what evidence; a bare LGTM says neither.
Swallowed exception
An error that is caught and then ignored, or logged where nobody will see it.
Default value
What a setting or parameter is when nobody sets it. Changing it changes behaviour for everyone who relied on it.
N+1 query
One query for a list, then one more for each item. Costly across a network; cheap in SQLite, so measure before judging.
Hypothesis log
A written record of hypotheses, predictions, experiments and results, kept while debugging.
Discriminating experiment
An experiment whose possible results differ between the hypotheses still standing.
git bisect
Binary search over history for the first commit where a check goes from good to bad.
Monotonic check
A check that is good before the culprit and bad after it, flipping exactly once.
Request id
A short id given to each request, written on every log line it causes and returned to the client.
Transactional outbox
Saving an outgoing message in the same transaction as the change it reports; a separate process sends it later.
Comprehension debt
The gap between the code a team has and the code the team understands.
